# Git: Теги, Релизы и Продвинутый Rebase — для Junior

## 🎯 Что это и зачем нужно?

Ты уже умеешь делать коммиты и ветки. Но как зафиксировать "Готовую версию 1.0"? И как навести порядок в бардаке из коммитов перед тем, как показать их тимлиду?

Здесь нам помогут:
1.  **Теги (Tags)** — чтобы запомнить важный момент в истории.
2.  **Релизы (Releases)** — чтобы красиво оформить этот момент для пользователей.
3.  **Интерактивный Rebase** — чтобы "причесать" историю коммитов.

---

## 🏷️ 1. Теги (Tags)

### ❌ Проблема:
Ты выпустил версию приложения, которая работает идеально. Спустя месяц и 1000 коммитов тебе говорят: *"Слушай, а та версия, которую мы показывали инвестору, где она?"*
И ты судорожно ищешь хеш коммита типа `a1b2c3d...`. Это неудобно.

### ✅ Решение: Тег
**Тег** — это просто наклейка с понятным именем (например, `v1.0.0`) на конкретный коммит. Она никуда не двигается (в отличие от ветки).

### Два вида тегов:

#### 1. Легковесный (Lightweight)
Просто указатель на коммит. Как закладка в книге.
```bash
git tag v1.0-beta
```

#### 2. Аннотированный (Annotated) — РЕКОМЕНДУЕТСЯ
Хранит имя автора, дату и сообщение (как коммит). Это "официальная" метка.
```bash
# -a = annotated, -m = сообщение
git tag -a v1.0.0 -m "Первый официальный релиз"
```

### Как отправить теги на сервер?
`git push` по умолчанию **НЕ отправляет** теги! Нужно делать это явно:
```bash
git push origin v1.0.0      # Отправить один тег
git push origin --tags      # Отправить ВСЕ теги сразу
```

## 📦 2. Релизы (Releases)

### В чём отличие от тега?
*   **Git** знает только про **Теги**.
*   **GitHub / GitLab** придумали **Релизы**.

**Релиз** — это красивая страница на GitHub, привязанная к **Тегу**.

### Что даёт Релиз:
1.  **Описание:** "Что нового в версии 1.0" (Changelog).
2.  **Файлы (Assets):** Можно прикрепить скомпилированный `.exe`, `.apk` или архив с кодом.
3.  **Маркетинг:** Это то, что видят пользователи, когда скачивают твою программу.

**Схема:**
`Код` → `Коммит` → `Тег (v1.0)` → `Релиз на GitHub (v1.0 + описание + файлы)`

## 🧹 3. Продвинутый Rebase (Интерактивный)

### ❌ Проблема:
Ты работал над фичей 3 дня. Твоя история коммитов выглядит так:
1. "Начал делать логин"
2. "Поправил опечатку"
3. "Забыл запятую"
4. "Вроде работает"
5. "Фикс багов"

Если ты отправишь это в `main`, тимлид будет плакать. Это "мусорная история".

### ✅ Решение: Interactive Rebase (`rebase -i`)
Это "машина времени", которая позволяет переписать историю **перед** тем, как отправить её всем.

### Как запустить?
Допустим, ты хочешь почистить последние 5 коммитов:
```bash
git rebase -i HEAD~5
```
*(Откроется текстовый редактор с планом действий)*

### Основные команды (что писать в редакторе):

1.  **`pick`** (по умолчанию) — оставить коммит как есть.
2.  **`reword` (r)** — оставить коммит, но **изменить текст сообщения** (если написал с ошибкой).
3.  **`squash` (s)** — **слить** этот коммит с предыдущим.
    *   *Пример:* Объединить "Поправил опечатку" с "Начал делать логин".
4.  **`fixup` (f)** — то же, что `squash`, но **выкидывает сообщение** этого коммита.
    *   *Идеально для:* "Забыл запятую" — изменения сольются, а мусорное сообщение исчезнет.
5.  **`drop` (d)** — **удалить** коммит полностью (будто его и не было).

### Живой пример: Чистим историю

**Было (в редакторе rebase):**
```
pick a1b2c Начал делать логин
pick d4e5f Поправил опечатку
pick g7h8i Забыл запятую
pick j9k0l Финальные правки
```

**Мы меняем на:**
```
reword a1b2c Реализация функционала Login  <-- Меняем имя на нормальное
fixup d4e5f Поправил опечатку            <-- Сольётся с верхним, сообщение исчезнет
fixup g7h8i Забыл запятую                <-- Сольётся с верхним, сообщение исчезнет
pick j9k0l Финальные правки              <-- Оставляем как есть
```

**Стало (после сохранения):**
1. "Реализация функционала Login" (внутри лежат изменения из 3-х старых коммитов)
2. "Финальные правки"

История чистая и красивая! ✨

---

## ⚠️ Важное правило безопасности

**Никогда не делай Rebase для веток, которые уже запушены и используются другими людьми!**

*   Rebase **переписывает** хеши коммитов.
*   Если коллега уже скачал твою ветку, а ты сделал rebase и запушил — у коллеги всё сломается.
*   **Правило:** Делай rebase только в своей **локальной** feature-ветке, пока никто не видит.

---

## 🎓 Чеклист для Junior

1.  Закончил версию? Поставь **Annotated Tag** (`git tag -a v1.0 -m "Release"`).
2.  Надо отправить теги? Не забудь `git push --tags`.
3.  Намусорил в коммитах? Используй `git rebase -i HEAD~N`, чтобы склеить (`squash/fixup`) мелкие правки в один нормальный коммит.
4.  Помни: Rebase меняет историю. Делай это только со своими личными ветками.
