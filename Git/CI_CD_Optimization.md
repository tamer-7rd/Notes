# Оптимизация CI/CD — конспект для интервью

> Формат: Senior объясняет Junior-у (стаж ~1 год), почему пайплайн тормозит и как это чинить.

---

## 1. 🧠 Ментальная модель

Представь **конвейер на заводе**.

- Каждый PR — это заготовка, которая едет по конвейеру.
- Станции конвейера: install → lint → test → build → deploy.
- Если конвейер работает 25 минут — разработчик сидит и ждёт. Умножь на 10 PR в день, 5 человек в команде — это **часы** потерянного времени каждый день.
- **Оптимизация CI/CD** — это ускорение конвейера без потери качества проверок.

**Главный принцип:** Быстрый фидбек = быстрая разработка. Если CI отвечает за 3 минуты, а не за 30 — разработчик не переключается на другую задачу, не теряет контекст и не пушит "fix ci" коммиты вслепую.

---

## 2. 💼 Зачем бизнесу быстрый CI/CD

| Проблема | Последствие | Метрика |
|----------|------------|---------|
| CI идёт 30 минут | Разработчики переключают контекст, теряют фокус | Developer Experience (DX) |
| Деплой раз в неделю | Фичи копятся, релиз становится рискованным | Deployment Frequency |
| Тесты нестабильные (flaky) | Люди игнорируют красный CI, баги попадают в прод | Change Failure Rate |
| Нет кэширования | Каждый запуск ставит зависимости с нуля — деньги и время | CI Cost ($) |

**На интервью спросят:** "Какие DORA-метрики вы знаете?"
- **Deployment Frequency** — как часто деплоим
- **Lead Time for Changes** — от коммита до прода
- **Change Failure Rate** — % деплоев, которые ломают прод
- **Time to Restore** — как быстро чиним прод после инцидента

## 3. 🔧 Техники оптимизации (от простого к сложному)

### 3.1 Кэширование зависимостей

**Проблема:** `npm install` / `pip install` каждый запуск качает всё с нуля — 2-5 минут впустую.

**Решение:** Кэшируем `node_modules` / `.venv` по хэшу lock-файла.

```yaml
# GitHub Actions — кэш для Node.js
- uses: actions/cache@v4
  with:
    path: node_modules
    key: node-${{ hashFiles('package-lock.json') }}
    restore-keys: node-
```

```yaml
# GitHub Actions — кэш для Python
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ hashFiles('requirements.txt') }}
```

**Результат:** Первый запуск — полный install. Все последующие (пока lock-файл не изменился) — секунды вместо минут.

**На интервью:** "Что будет, если закэшировать `node_modules` по хэшу `package.json` вместо `package-lock.json`?"
— Плохая идея. `package.json` содержит диапазоны версий (`^1.2.3`), а `lock` — точные. Можно получить кэш с устаревшими пакетами.

---

### 3.2 Параллельные джобы (Matrix / Parallel Jobs)

**Проблема:** Lint → Test → Build идут последовательно. Общее время = сумма всех шагов.

**Решение:** Разнеси независимые шаги в параллельные джобы.

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  build:
    needs: [lint, test]  # ждёт обе джобы
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run build
```

**Было:** lint (2 мин) → test (5 мин) → build (3 мин) = **10 мин**
**Стало:** lint (2 мин) + test (5 мин) параллельно → build (3 мин) = **8 мин**

Экономия растёт, когда тестовых сьютов много — можно разбить тесты на shards.

---

### 3.3 Test Sharding (параллелизация тестов)

**Проблема:** 500 тестов идут 15 минут на одном раннере.

**Решение:** Разбить тесты на N частей и запустить параллельно.

```yaml
jobs:
  test:
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx vitest --shard=${{ matrix.shard }}/4
```

**Было:** 500 тестов × 1 раннер = 15 минут
**Стало:** 125 тестов × 4 раннера = ~4 минуты

**Нюанс:** Шарды должны быть примерно равными по времени. Иначе один шард закончит за 1 мин, а другой будет пыхтеть 12 мин — толку мало.

### 3.4 Conditional Runs (запуск только нужного)

**Проблема:** Изменил README — а CI гоняет все тесты, линт и билд 15 минут.

**Решение:** Path-фильтры — запускай джобы только при изменении нужных файлов.

```yaml
on:
  push:
    paths:
      - 'src/**'
      - 'tests/**'
      - 'package.json'
      - 'package-lock.json'
    paths-ignore:
      - '**.md'
      - 'docs/**'
```

**Продвинутый вариант (monorepo):**

```yaml
jobs:
  detect-changes:
    outputs:
      backend: ${{ steps.filter.outputs.backend }}
      frontend: ${{ steps.filter.outputs.frontend }}
    steps:
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            backend:
              - 'backend/**'
            frontend:
              - 'frontend/**'

  test-backend:
    needs: detect-changes
    if: needs.detect-changes.outputs.backend == 'true'
    # ...

  test-frontend:
    needs: detect-changes
    if: needs.detect-changes.outputs.frontend == 'true'
    # ...
```

### 3.5 Docker Layer Caching

**Проблема:** Docker build пересобирает все слои каждый запуск — 5-10 минут.

**Решение:** Кэшируй Docker-слои + правильно структурируй Dockerfile.

```dockerfile
# ❌ Плохо — любое изменение кода инвалидирует кэш зависимостей
COPY . .
RUN npm install

# ✅ Хорошо — зависимости кэшируются отдельно от кода
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
```

```yaml
# GitHub Actions — Docker layer cache
- uses: docker/build-push-action@v5
  with:
    context: .
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

**На интервью:** "Почему `npm ci` а не `npm install` в Docker?"
— `npm ci` удаляет `node_modules` и ставит строго по `lock`-файлу. Это детерминированно и быстрее в CI.

### 3.6 Self-hosted Runners

**Проблема:** GitHub-hosted раннеры — это виртуалки, которые стартуют с нуля каждый запуск. Плюс у бесплатных — лимиты по минутам.

**Решение:** Свои раннеры (bare metal / VM в облаке).

| | GitHub-hosted | Self-hosted |
|--|--------------|------------|
| Старт | Холодный, ~20-40 сек | Горячий, мгновенный |
| Кэш | Сетевой (медленнее) | Локальный диск (быстрее) |
| Стоимость | $0.008/мин (Linux) | Стоимость сервера |
| Безопасность | Изолированный | Надо настраивать самим |

**Когда переходить:** Когда CI-бюджет превышает стоимость собственного сервера, или когда нужны GPU / специфичное железо.

---

### 3.7 Flaky Tests — тихий убийца CI

**Проблема:** Тест проходит 9 из 10 раз. Разработчики начинают перезапускать CI "ну может пройдёт" — это **культурная деградация**.

**Стратегия:**
1. **Quarantine** — вынеси flaky-тесты в отдельный сьют. Они запускаются, но не блокируют PR.
2. **Retry (осторожно)** — допустим 1 retry, но логируй каждый flake.
3. **Track & Fix** — дашборд с процентом flaky-тестов. Если > 5% — красная зона, останавливай фичи и фикси тесты.

```yaml
# Пример retry в GitHub Actions
- run: npm test
  id: tests
  continue-on-error: true

- if: steps.tests.outcome == 'failure'
  run: npm test  # retry один раз
```

**На интервью:** "Как вы боретесь с flaky-тестами?" — Один из любимых вопросов. Показывает, что ты не просто пишешь тесты, а думаешь о надёжности CI-системы в целом.

## 4. 🏗️ Продвинутые паттерны

### 4.1 Merge Queue (GitHub Merge Queue)

**Проблема:** 5 PR прошли CI параллельно, но при мерже конфликтуют друг с другом.

**Решение:** Merge Queue — GitHub автоматически проверяет PR **вместе** с другими PR из очереди.

```
PR #1 ──┐
PR #2 ──┼── merge queue → CI runs on combined code → merge
PR #3 ──┘
```

Включается в Settings → Branch Protection → Require merge queue.

---

### 4.2 Canary / Blue-Green Deploys

**Суть:** Не деплой на 100% трафика сразу.

- **Canary:** Новая версия получает 5% трафика. Если метрики ок → постепенно увеличиваем до 100%.
- **Blue-Green:** Две идентичные среды. Blue = текущий прод. Green = новая версия. Переключаем роутер. Если сломалось — мгновенный откат.

**На интервью:** "Расскажите про стратегии деплоя" — это обязательный вопрос уровня Middle+.

---

### 4.3 Artifact Reuse (не собирай дважды)

**Проблема:** Собрали Docker-образ в CI для тестов. Потом собираем заново для деплоя — зря тратим время.

**Решение:** Собираем артефакт один раз, передаём между джобами.

```yaml
jobs:
  build:
    steps:
      - run: docker build -t myapp:${{ github.sha }} .
      - run: docker push registry/myapp:${{ github.sha }}

  test:
    needs: build
    steps:
      - run: docker pull registry/myapp:${{ github.sha }}
      - run: docker run myapp:${{ github.sha }} npm test

  deploy:
    needs: test
    steps:
      - run: docker pull registry/myapp:${{ github.sha }}
      # деплоим тот же самый образ, который прошёл тесты
```

**Принцип:** "Build once, deploy everywhere" — один артефакт проходит все стадии.

## 5. 📊 Как измерять эффективность CI/CD

### Метрики, которые стоит трекать:

| Метрика | Хорошо | Плохо |
|---------|--------|-------|
| Среднее время CI | < 5 мин | > 15 мин |
| % flaky тестов | < 1% | > 5% |
| Deployment Frequency | Несколько раз в день | Раз в неделю/месяц |
| Lead Time (commit → prod) | < 1 день | > 1 неделя |
| Change Failure Rate | < 5% | > 15% |
| MTTR (время восстановления) | < 1 час | > 1 день |

**Инструменты:** GitHub Actions Insights, Datadog CI Visibility, BuildPulse (для flaky-тестов).

## 6. 🚧 Чек-лист оптимизации CI/CD

Прежде чем лезть в пайплайн, спроси себя:

- [ ] **Что самое медленное?** — Открой CI лог, найди bottleneck. Обычно это install или тесты.
- [ ] **Есть ли кэширование?** — Зависимости, Docker-слои, билд-артефакты.
- [ ] **Можно ли параллелить?** — Lint и тесты не зависят друг от друга.
- [ ] **Запускаю ли лишнее?** — Path-фильтры, conditional jobs.
- [ ] **Тесты стабильны?** — Flaky-тесты подрывают доверие к CI.
- [ ] **Артефакт собирается один раз?** — Build once, deploy everywhere.
- [ ] **Есть ли стратегия деплоя?** — Canary / Blue-Green / Rolling update.
- [ ] **Метрики трекаются?** — Нельзя улучшить то, что не измеряешь.

## 7. 🎯 Типичные вопросы на интервью

**Q: Как ускорить CI-пайплайн, который работает 20 минут?**
A: Диагностика → кэширование зависимостей → параллельные джобы → test sharding → path-фильтры → Docker layer caching. Обычно одного кэширования хватает, чтобы срезать 30-50%.

**Q: Чем отличается Continuous Delivery от Continuous Deployment?**
A: Delivery = артефакт готов к деплою, но нужен ручной апрув. Deployment = автоматический деплой после прохождения всех проверок. На практике большинство команд начинают с Delivery и переходят к Deployment, когда доверяют своему тестовому покрытию.

**Q: Как бороться с flaky-тестами?**
A: Карантин + трекинг + retry с логированием. Главное — не игнорировать. Flaky-тесты разрушают культуру: если CI "иногда красный" — люди перестают обращать внимание.

**Q: Что такое Merge Queue и зачем?**
A: Очередь мержа. PR проверяются не изолированно, а в комбинации с другими PR из очереди. Решает проблему "каждый PR зелёный по отдельности, но вместе ломают main".

**Q: Build once, deploy everywhere — что это?**
A: Один и тот же артефакт (Docker-образ, бинарник) проходит все среды: test → staging → prod. Не пересобираем на каждом этапе. Конфигурация среды приходит извне (env vars, configmaps), а не зашита в артефакт.

**Q: Какие DORA-метрики вы знаете и зачем?**
A: Deployment Frequency, Lead Time, Change Failure Rate, MTTR. Это индустриальный стандарт от Google (DORA research). Позволяет объективно оценить зрелость DevOps-процессов в команде.

## Итого: Формула быстрого CI/CD

```
Быстрый CI = Кэш + Параллелизм + Фильтры + Стабильные тесты
Надёжный CD = Один артефакт + Стратегия деплоя + Мониторинг + Откат
```

Не нужно внедрять всё сразу. Начни с **измерения** (сколько минут CI?), потом **кэширование**, потом **параллельность**. Этих трёх шагов обычно хватает, чтобы из 20 минут сделать 5.
