# Git: Полный цикл dev → PR → merge → деплой

## 1. 🧠 Ментальная модель (Аналогия из жизни)

Представь **издательство крупной газеты**.

*   **Main ветка (Production)** — это готовый, напечатанный тираж утренней газеты, который уже читают люди. В нем *не может* быть опечаток или пустых страниц.
*   **Feature ветка** — это черновик журналиста. Он пишет статью на своем столе. Никто другой пока этого не видит.
*   **Pull Request (PR)** — это момент, когда журналист кладет статью на стол редактору. "Проверь, пожалуйста".
*   **Code Review** — редактор читает, черкает красной ручкой: "Тут заголовок кликбейтный, тут факты не проверены, а тут запятой нет". Журналист идет исправлять.
*   **CI (Continuous Integration)** — это автоматический корректор, который проверяет орфографию и стиль (linter), и верстальщик, который пробует разместить статью на макете (build/tests). Если статья не влезает или текст серый на сером фоне — процесс стопорится.
*   **Merge** — статья утверждается главным редактором и вклеивается в макет завтрашнего номера.
*   **Deploy** — печатный станок запускается, и газета разлетается по киоскам.

**Суть:** Мы не пишем сразу в чистовик. Мы создаем изолированное пространство для хаоса (ветка), приводим его в порядок (review & CI), и только идеальный результат добавляем в общий продукт.

## 2. 💼 Зачем это нужно бизнесу и архитектуре

Почему нельзя просто писать в `main` и заливать по FTP?

**Для Бизнеса:**
1.  **Time-to-Market (TTM) без страха:** Четкий пайплайн позволяет диплоить фичи 10 раз в день. Если процесс налажен, бизнес не боится релиза в пятницу вечером.
2.  **Стабильность (Uptime):** CI/CD и Code Review — это фильтры. Они отсеивают 90% багов до того, как их увидит пользователь.
3.  **Bus Factor:** Код становится коллективным владением. Если автор фичи заболел, команда видит историю изменений и контекст в PR.

**Для Архитектуры:**
1.  **Code Ownership & Quality:** PR — это ворота качества. Мы не пускаем "грязный" код, который нарушает архитектурные слои.
2.  **Audit Trail:** Git history — это юридический документ разработки. Кто, когда и *зачем* (главное!) изменил эту строчку.
3.  **Изоляция изменений:** Если фича A сломала всё, мы можем её откатить (revert) или просто не мержить, не блокируя фичу B.

## 3. 🔄 Эталонный цикл разработки (The Flow)

Как это делает Senior разработчик:

### Шаг 1: Подготовка (Pre-coding)
*   **Sync:** `git checkout main && git pull`. Всегда стартуй с актуальной версии.
*   **Branch naming:** `feature/JIRA-123-add-login` или `fix/user-auth-error`. Имя ветки должно говорить *что* и *зачем*.

### Шаг 2: Разработка (Coding)
*   **Atomic Commits:** Делай коммиты логическими квантами.
    *   ❌ "WIP", "Fix", "Update" (300 файлов изменений).
    *   ✅ "Add LoginButton component", "Implement auth service logic", "Add unit tests for auth".
*   **Local Testing:** Запусти тесты *до* того, как пушить.

### Шаг 3: Синхронизация (Keep it fresh)
Пока ты писал код 3 дня, `main` ушел вперед.
*   **Rebase:** Используй `git fetch origin && git rebase origin/main` (предпочтительнее merge для чистой истории). Ты как бы "перекладываешь" свои изменения поверх свежего кода.

### Шаг 4: Pull Request (The Art of PR)
PR — это письмо команде.
*   **Title:** Четкий и понятный.
*   **Description:**
    *   **What:** Что сделано?
    *   **Why:** Зачем? Ссылка на задачу.
    *   **How to test:** Инструкция для ревьюера (какие кнопки жать, под каким юзером зайти).
    *   **Screenshots/GIFs:** Для UI задач — обязательно. "Лучше один раз увидеть".
*   **Self-review:** *Сам* пройдись по своему PR, прежде чем кидать ссылку коллегам. Убери `console.log`, поправь отступы.

### Шаг 5: Code Review & Iteration
*   Не спорь ради спора. Если предлагают лучшее решение — принимай. Если не согласен — аргументируй технически, а не "я так вижу".
*   Fixup commits: Во время правок не плоди мусорные коммиты ("fix", "fix 2"). Либо используй `git commit --amend`, либо делай squash при мерже.

### Шаг 6: Merge & Deploy
*   **Squash and Merge:** Стандарт индустрии. Твои 15 коммитов разработки схлопываются в один чистый коммит в истории `main`: "Feat: Add login flow (JIRA-123)".
*   **CI/CD Pipeline:**
    1.  Install dependencies.
    2.  Linting & Formatting check.
    3.  Unit & Integration Tests.
    4.  Build (Webpack/Vite/Go build).
    5.  Deploy to Staging (авто) -> Smoke Tests.
    6.  Deploy to Prod (руками или авто после апрува).

## 4. 🚧 Подводные камни и Best Practices

### 1. Гигантские PR (The Monster PR)
*   **Проблема:** PR на +2000 строк. Никто его реально не проверит. Ревьюер напишет "LGTM" (Looks Good To Me) и пойдет пить кофе.
*   **Решение:** Декомпозиция. Разбей задачу на 3 PR:
    1.  API contracts & Models.
    2.  Backend Logic.
    3.  Frontend UI.

### 2. "На моем компе работает"
*   **Проблема:** Разные версии Node.js, БД, локальные конфиги.
*   **Решение:** Docker для локальной разработки. CI среда должна быть максимально похожа на Prod.

### 3. Force Push в общую ветку
*   **Табу:** Никогда не делай `git push -f` в `main` или `develop`. Ты перепишешь историю и сломаешь жизнь всей команде.
*   **Исключение:** Твоя личная фича-ветка, *пока* ее никто другой не трогает (например, после rebase).

### 4. Игнорирование CI
*   **Проблема:** Тесты упали, но "это флакающий тест, я знаю, что код норм", и мы форсим мерж.
*   **Последствие:** Сломанный прод.
*   **Правило:** Красный CI = Нет мержа. Точка.

### 5. Забытые миграции БД
*   **Проблема:** Код требует новую колонку в таблице, код задеплоился, а миграция не применилась. Приложение падает с 500 ошибкой.
*   **Решение:** Миграции должны быть частью деплой-процесса и быть идемпотентными.

## Итого: Чек-лист Senior-разработчика

1.  Ветка от актуального `main`.
2.  Код написан, тесты написаны и проходят локально.
3.  PR создан с внятным описанием и скриншотами.
4.  CI зеленый.
5.  Получено 1-2 апрува.
6.  Код вмержен (Squash).
7.  Ветка удалена.
8.  Мониторинг прода после деплоя (не уходи сразу на обед!).
