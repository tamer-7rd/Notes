# Введение в рекурсию (Introduction to recursion)

> *Если вы уже хорошо понимаете рекурсию, вы можете пропустить эту статью.*

## Основные понятия
Рекурсия — это метод решения проблем. В коде рекурсия реализуется с помощью функции, которая вызывает саму себя.

Противоположностью рекурсивного алгоритма является итеративный алгоритм. Существует [раздел теории (теория вычислимости)](https://en.wikipedia.org/wiki/Computability_theory), который доказывает, что любой итеративный алгоритм может быть записан рекурсивно. В то время как итеративные алгоритмы используют циклы `for` и `while` для имитации повторения, рекурсивные алгоритмы используют вызовы функций для моделирования той же логики.

### Пример: вывод чисел
Допустим, мы хотим вывести числа от 1 до 10. Вот псевдокод для итеративного алгоритма:

```python
for i in range(1, 11):
    print(i)
```

Вот псевдокод для эквивалентного рекурсивного алгоритма:

```python
def fn(i):
    print(i)
    fn(i + 1)
    return

fn(1)
```

Каждый вызов `fn` сначала выводит `i` (которое начинается с 1), а затем снова вызывает `fn`, но увеличивая `i` (чтобы вывести следующее число).

> Первый вызов функции выводит `1`, затем вызывает `fn(2)`. В контексте вызова `fn(2)` выводится `2`, а затем вызывается `fn(3)` и так далее.

Однако этот код на самом деле неправильный. Видите проблему? Вызовы функций никогда не остановятся! Выполнение этого кода будет крутить бесконечный цикл вывода натуральных чисел (положительных целых чисел) до бесконечности (или пока компьютер не выдаст ошибку переполнения стека). Код никогда не дойдёт до оператора `return` на последней строке, потому что строка `fn(i + 1)` всегда срабатывает раньше него.

## Базовый случай (Base case)
Для того чтобы рекурсия остановилась, нам нужно то, что называется **базовым случаем** (base case). 
Базовые случаи — это условия (обычно в самом начале рекурсивных функций), которые завершают вызовы функции (делают `return`).

```python
def fn(i):
    if i > 10:
        return

    print(i)
    fn(i + 1)
    return

fn(1)
```

> После того как мы вызываем `fn(10)`, мы выводим `10` и вызываем `fn(11)`. В вызове `fn(11)` срабатывает базовый случай, и происходит возврат (`return`). Теперь мы возвращаемся обратно в вызов `fn(10)` и переходим к следующей строке — оператору `return`. Это возвращает нас обратно в вызов `fn(9)` и так далее, пока мы в конечном итоге не вернемся из вызова `fn(1)` и алгоритм не завершит свою работу.

## Порядок выполнения (Order of execution)
Важная вещь, которую нужно понимать о рекурсии, — это порядок (очередность), в котором выполняется код: порядок, в котором компьютер выполняет инструкции. С итеративной программой всё просто: выполнение начинается сверху и идёт построчно вниз. В рекурсии же всё может запутываться, так как вызовы могут наслаиваться друг на друга. 
Давайте снова выведем числа, но теперь только до 3. Давайте также добавим еще один оператор вывода (`print`) и пронумеруем строки кода:

```python
def fn(i):
1.  if i > 3:
2.      return
3.  print(i)
4.  fn(i + 1)
5.  print(f"End of call where i = {i}")
6.  return

fn(1)
```

Если вы запустите этот код, вы увидите следующий вывод:
```
// 1
// 2
// 3
// End of call where i = 3
// End of call where i = 2
// End of call where i = 1
```

Как видите, строка текста (**строка 5**) выполняется в **обратном порядке**. 
1. Исходный вызов `fn(1)` сначала выводит `1`, затем вызывает `fn(2)`. 
2. `fn(2)` выводит `2`, затем вызывает `fn(3)`. 
3. `fn(3)` выводит `3`, затем вызывает `fn(4)`. 
4. **Теперь важный момент (как рекурсия «движется» обратно «вверх»):** в вызове `fn(4)` срабатывает базовый случай, который делает возврат (`return`). 
5. Теперь мы возвращаемся назад в вызов функции, где `i = 3`, и **строка 4 (`fn(i + 1)`) завершила свое выполнение**, поэтому мы переходим к следующей **строке 5**, которая выводит `"End of call where i = 3"`. Как только эта строка выполнилась, мы переходим к следующей строке — `return` (**строка 6**). 
6. Теперь мы снова оказываемся выше по цепочке, внутри вызова, где `i = 2`, и здесь **строка 4 завершила свое выполнение**. Мы снова переходим к следующей строке (**строка 5**) и выводим `"End of the call where i = 2"`. 
7. Это поведение повторяется до тех пор, пока первоначальный вызов функции `fn(1)` не выполнит свой `return` и алгоритм не завершится.

> Каждый вызов функции "существует" в памяти до тех пор, пока он не сделает возврат (`return`). Когда мы переходим к другому вызову функции, старый вызов ожидает, пока новый не вернет управление. Порядок вызовов запоминается, а строки внутри функций выполняются строго по порядку.
>
> Обратите внимание, что каждый вызов функции также имеет свою **локальную область видимости** (local scope). Так, в примере выше, когда мы вызываем `fn(3)`, в памяти одновременно существуют 3 «версии» переменной `i`:
> - В первом вызове `i = 1`
> - Во втором вызове `i = 2`
> - В третьем вызове `i = 3`
>
> Допустим, мы сделали бы `i += 1` внутри вызова `fn(3)`. Тогда значение `i` стало бы равным `4`, но **только** внутри вызова `fn(3)`. Две другие «версии» переменной `i` остались бы нетронутыми, потому что они находятся в разных областях видимости (scopes).

## Разбиение задач на части (Breaking problems down)
Этот пример с выводом чисел довольно бессмысленен — гораздо проще использовать цикл `for`, если вам нужно просто напечатать числа. 
Рекурсия раскрывается во всей красе тогда, когда вы используете её для разбиения задачи на **«подзадачи»** (subproblems), решения которых затем можно объединить для решения исходной задачи.

### Числа Фибоначчи
Давайте посмотрим на [числа Фибоначчи](https://en.wikipedia.org/wiki/Fibonacci_number). Числа Фибоначчи — это последовательность чисел, начинающаяся с `0, 1`. Затем каждое последующее число определяется как сумма двух предыдущих: `0, 1, 1, 2, 3, 5, 8...`

Более формально мы имеем уравнение:

> $F_n = F_{n-1} + F_{n-2}$

Это называется **рекуррентным соотношением** (recurrence relation) — уравнением, которое связывает элементы последовательности вместе.

Давайте напишем функцию `F(n)`, которая возвращает $n$-ное число Фибоначчи (с индексом от 0). Не забывайте, что любой рекурсивной функции нужны базовые случаи. В случае Фибоначчи базовые случаи определены явно: `F(0) = 0` и `F(1) = 1`.

```python
def F(n):
    # Базовые случаи
    if n <= 1:
        return n
    
    # Рекуррентное соотношение
    oneBack = F(n - 1)
    twoBack = F(n - 2)
    return oneBack + twoBack
```

Допустим, мы хотим найти `F(3)`. При вызове `F(3)` мы бы увидели следующий поток выполнения (каждый уровень отступа представляет область видимости вызова функции):

```
oneBack = F(2)
    oneBack = F(1)
        F(1) = 1
    twoBack = F(0)
        F(0) = 0
    F(2) = oneBack + twoBack = 1
twoBack = F(1)
    F(1) = 1
F(3) = oneBack + twoBack = 2
```

Как видите, мы взяли исходную проблему `F(3)` и разбили её на две меньшие подзадачи — `F(2)` и `F(1)`. Объединив рекуррентное соотношение и базовые случаи, мы смогли решить эти подзадачи и использовать их решения для ответа на наш изначальный вопрос.

Это самое распространенное применение рекурсии — ваша рекурсивная функция **возвращает ответ на проблему, которую вы пытаетесь решить для данного ввода**. В этом примере проблема, которую мы пытаемся решить для заданного ввода: *«Каким является $n$-ное число Фибоначчи?»*. Поэтому мы спроектировали нашу функцию так, чтобы она возвращала число Фибоначчи в соответствии с входным аргументом $n$. Определив базовые случаи и рекуррентное соотношение, мы можем легко реализовать данную функцию.

Следуя этой идее, решение подзадач становится тривиальным: если бы мы хотели найти 100-е число Фибоначчи, мы по определению знаем, что оно является суммой 99-го и 98-го чисел Фибоначчи. При вызове `F(100)`, вызовы подзадач `F(99)` и `F(98)` предоставят нам необходимые числа.

## Зачем мы вообще изучаем Фибоначчи?

Это очень правильный и честный вопрос, потому что в реальной работе числа Фибоначчи сами по себе почти никогда не нужны. Фибоначчи — это своего рода тренировочный манекен. Как груша в боксе — никто не дерётся с грушей на улице, но на ней ставят удар. 

В данном случае **вы учите не числа Фибоначчи, вы учитесь алгоритмическому мышлению**.

### Что реально здесь тренируется?
Когда вы смотрите на уравнение $F(n) = F(n-1) + F(n-2)$, вы учитесь видеть проблему под другим углом: **большую задачу можно выразить через более маленькие версии самой себя**. 
Это фундаментальный принцип для 80% сложных алгоритмов.

### Где это применяется на практике?

**1. Динамическое программирование (Dynamic Programming)**
Это половина всех задач на платформе LeetCode и база для собеседований в Google, Meta, Amazon.
Самые частые задачи звучат так:
- Найти минимальную стоимость (minimum cost)
- Найти максимальную прибыль (maximum profit)
- Найти кратчайший путь (shortest path)
- Посчитать количество способов сделать что-либо
- Найти оптимальное решение

Все они строятся по одному шаблону: 
> `Ответ(n) = лучший вариант из предыдущих состояний + новый выбор`

Например, сколько есть способов подняться по лестнице, если можно шагать на 1 или на 2 ступеньки? 
`ways(n) = ways(n-1) + ways(n-2)`. Это та же самая логика Фибоначчи!

**2. Разделяй и властвуй (Divide & Conquer)**
Популярные алгоритмы вроде сортировки слиянием (Merge Sort), быстрой сортировки (Quick Sort) и бинарного поиска (Binary Search) работают по идее: *реши маленькие части $\rightarrow$ объедини их в общий результат*. Это та же философия, что и в базовой рекурсии.

**3. Понимание рекурсивных структур**
Без нормального понимания рекурсии невозможно освоить:
- Деревья (Trees) и графы (Graphs)
- Алгоритм поиска в глубину (DFS)
- Поиск с возвратом (Backtracking)
- Обход файловой системы (ведь папка содержит папки, которые содержат папки...)
- Процесс сверки в React (React reconciliation) — да, там тоже активно используется рекурсия.

**4. Оптимизация и понимание медленного алгоритма**
Числа Фибоначчи показывают нам важную вещь: наивный, красивый на вид код способен работать ужасно медленно. 
Код `F(n-1) + F(n-2)` заставляет компьютер повторять одни и те же вычисления множество раз. Это закладывает понимание того, откуда берутся **мемоизация (memoization)**, **кэширование (caching)**, **динамическое программирование** и оптимизация ресурсов времени. Это и есть инженерное мышление.

### Самая важная правда

Senior-разработчик, глядя на новую сложную задачу, практически мгновенно задает себе вопрос: 
**"Могу ли я выразить это через меньшую версию этой же задачи?"**

Если ответ "да" — задача почти решена. Пример с числами Фибоначчи — это первый раз, когда ваш мозг учится этому специфическому рефлексу. Индустрия редко требует писать сам алгоритм Фибоначчи, но она постоянно требует решать задачи, где "лучшее решение сейчас" базируется на "лучшем решении вчера + новый выбор".

Если этот паттерн не встроен в мышление — алгоритмы выглядят как хаос из независимых тем. Если встроен — задачи начинают повторяться. В какой-то момент алгоритмы действительно перестают казаться набором разных задач и превращаются в 5–6 повторяющихся идей. И числа Фибоначчи — это самая первая дверь в эту комнату.
