# Как объяснить архитектуру на собесе — для Junior

## 🎯 Почему спрашивают об архитектуре?

Интервьюер хочет понять:
1. Понимаешь ли ты, как устроен твой проект
2. Можешь ли объяснить техническое решение
3. Думаешь ли о структуре, а не только о коде

**Типичные вопросы:**
- "Расскажи об архитектуре проекта"
- "Как устроен твой проект?"
- "Какие слои есть в приложении?"

---

## 📝 Структура ответа

### 1. Общая картина (30 сек)
```
"Проект построен на классической клиент-серверной архитектуре:
- Фронтенд: React SPA
- Бэкенд: Node.js REST API
- База данных: PostgreSQL"
```

### 2. Структура фронтенда (30 сек)
```
"На фронте я разделил код на:
- Компоненты (UI-элементы)
- Хуки (логика и состояние)
- API-слой (запросы к бэку)
- Утилиты (вспомогательные функции)"
```

### 3. Структура бэкенда (30 сек)
```
"На бэке использую слоёную архитектуру:
- Routes (маршруты)
- Controllers (обработка запросов)
- Services (бизнес-логика)
- Repositories (работа с БД)"
```

### 4. Взаимодействие (30 сек)
```
"Фронт общается с бэком через REST API.
Запросы идут через axios, ответы в JSON.
Аутентификация через JWT в заголовках."
```

---

## 🎬 Полный пример ответа

```
"Мой проект построен на клиент-серверной архитектуре.

Фронтенд — это React SPA. Структура:
- components/ — UI-компоненты (кнопки, формы, карточки)
- hooks/ — кастомные хуки для логики (useAuth, useApi)
- api/ — функции для запросов к бэку
- pages/ — страницы приложения

Бэкенд — Node.js с Express. Использую слоёную архитектуру:
- Routes принимают HTTP-запросы
- Controllers валидируют данные и вызывают сервисы
- Services содержат бизнес-логику
- Repositories работают с базой данных

База данных — PostgreSQL. Использую Prisma как ORM.

Взаимодействие:
- Фронт отправляет запросы через axios
- Бэк возвращает JSON
- Аутентификация через JWT в HTTP-only cookies

Такая структура помогает разделять ответственность: 
если нужно изменить логику — иду в сервисы, 
если UI — в компоненты."
```

## 📊 Визуализация архитектуры

### Простая схема для объяснения:

```
┌─────────────┐     HTTP/JSON     ┌─────────────┐
│   Frontend  │ ◄───────────────► │   Backend   │
│   (React)   │                   │  (Node.js)  │
└─────────────┘                   └──────┬──────┘
                                         │
                                         │ SQL
                                         ▼
                                  ┌─────────────┐
                                  │  Database   │
                                  │ (PostgreSQL)│
                                  └─────────────┘
```

### Структура бэкенда:

```
┌───────────────────────────────────────┐
│              Routes                    │  ← HTTP endpoints
├───────────────────────────────────────┤
│            Controllers                 │  ← Валидация, ответы
├───────────────────────────────────────┤
│             Services                   │  ← Бизнес-логика
├───────────────────────────────────────┤
│           Repositories                 │  ← Работа с БД
├───────────────────────────────────────┤
│             Database                   │  ← PostgreSQL
└───────────────────────────────────────┘
```

## 💡 Как объяснить паттерны

### MVC:
```
"Использую MVC-подобную структуру:
- Model — это сервисы и репозитории (данные и логика)
- View — React-компоненты (отображение)
- Controller — роуты и контроллеры на бэке (обработка запросов)"
```

### Слоёная архитектура:
```
"Бэкенд разделён на слои по ответственности:
- Presentation layer (роуты, контроллеры) — работа с HTTP
- Business layer (сервисы) — бизнес-логика
- Data layer (репозитории) — работа с БД

Каждый слой зависит только от слоя ниже."
```

### Dependency Injection:
```
"Сервисы получают зависимости через конструктор.
Например, UserService получает UserRepository.
Это помогает тестировать — могу подставить mock-репозиторий."
```

## ❓ Частые вопросы

### "Почему такая архитектура?"
```
"Выбрал слоёную архитектуру, потому что:
1. Легко поддерживать — каждый слой отвечает за своё
2. Легко тестировать — могу тестировать слои отдельно
3. Легко расширять — добавление новой фичи не ломает старые"
```

### "Что бы изменил?"
```
"Добавил бы middleware для валидации на уровне роутов.
Сейчас валидация размазана по контроллерам."
```

### "Как масштабируется?"
```
"Для масштабирования можно:
- Вынести тяжёлые операции в очередь (Redis/RabbitMQ)
- Добавить кэширование (Redis)
- Разделить на микросервисы, если проект вырастет"
```

---

## ❌ Частые ошибки

### 1. Путаница в терминах
```
❌ "У меня MVC: React — это View, Node — это Controller, 
    PostgreSQL — это Model"
✅ "Использую клиент-серверную архитектуру с REST API"
```

### 2. Нет объяснения "почему"
```
❌ "Разделил на папки components, hooks, api..."
✅ "Разделил по ответственности: компоненты для UI, 
    хуки для логики, api для запросов"
```

### 3. Слишком много деталей
```
❌ "В папке components есть Button.tsx, Input.tsx, Card.tsx..."
✅ "Компоненты разделены на UI-элементы и страницы"
```

## 🎓 Главное:

1. **Общая картина:** Клиент → Сервер → БД
2. **Слои:** Разделение по ответственности
3. **Почему:** Объясни причину выбора архитектуры
4. **Простота:** Не усложняй, говори о том, что реально есть
5. **Честность:** Если чего-то нет — скажи, что добавил бы

**Запомни:** Архитектура — это не про сложные слова, а про понимание, как части проекта работают вместе!
