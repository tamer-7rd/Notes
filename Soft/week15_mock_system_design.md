# Mock-собес по System Design (Week 15)

## Цель
Провести полноценную симуляцию System Design интервью. Не просто знать компоненты, а уметь **вести диалог** — задавать вопросы, рисовать схему, обосновывать решения и обсуждать trade-offs. На этой секции проверяют не "правильный ответ", а **мышление**.

> Формат: Senior ведёт mock-собес с Junior-ом (стаж ~1 год) и объясняет, что и зачем.

## 1. Как проходит System Design интервью (тайминг 45-60 мин)

    +---------------------------+----------+---------------------------+------------------------------------------+
    | Этап                       | Время    | Что делаешь               | Частая ошибка Junior-а                   |
    +---------------------------+----------+---------------------------+------------------------------------------+
    | Уточнение требований       | 5-10 мин | Задаёшь вопросы            | Сразу рисуешь квадраты                  |
    | Оценка нагрузки           | 3-5 мин  | Считаешь "на салфетке"     | Пропускаешь — потом не можешь обосновать |
    |                           |          |                            | выбор БД                                 |
    | High-Level Design         | 10-15 мин| Рисуешь основные блоки    | Рисуешь слишком детально слишком рано     |
    | Deep Dive                 | 15-20 мин| Углубляешься в 2-3 комп.   | Пытаешься покрыть ВСЁ — поверхностно     |
    | Масштабирование и         | 5-10 мин | Обсуждаешь узкие места и   | Забываешь сказать "что будет, если       |
    | bottlenecks               |          | отказоустойчивость         | упадёт X"                                |
    +---------------------------+----------+---------------------------+------------------------------------------+

**Золотое правило:** Интервьюер хочет видеть **диалог**, а не монолог. Спрашивай: "Мне углубиться в хранение данных или в real-time часть?" — ты показываешь, что умеешь приоритизировать.

## 2. Пошаговый разбор: "Design URL Shortener" (Живой пример)

Представь, что интервьюер сказал: *"Давай спроектируем сервис вроде bit.ly"*.

### Шаг 1: Уточнение требований

**Не молчи. Задавай вопросы.**

> Junior молча начинает рисовать базу данных.
> Senior: "Стоп. Ты ещё не знаешь, что именно проектируешь."

Правильные вопросы:
*   "Какой объём? Сколько URL сокращаем в день?" — *допустим, 100M новых URL/день*
*   "Соотношение чтение/запись?" — *100:1 (read-heavy)*
*   "Время жизни ссылки? Удаляются ли старые?" — *хранятся 5 лет*
*   "Нужна ли кастомизация? (`bit.ly/my-brand`)" — *пока нет, MVP*
*   "Аналитика (сколько кликов)?" — *да, базовая*
*   "Какая доступность нужна?" — *99.9%*

**Зачем:** Без этого ты не знаешь, нужен ли тебе шардинг, какой тип БД выбрать и какой SLA держать.

### Шаг 2: Оценка нагрузки (Back-of-the-envelope)

```
Записи: 100M URL/день ≈ 1200 URL/сек
Чтения: 100:1 → 120,000 RPS на чтение
Хранение: 100M × 365 × 5 лет ≈ 180 млрд записей
          Каждая запись ~500 bytes → 180B × 500B ≈ 90 TB данных
Bandwidth: 120K RPS × 500B ≈ 60 MB/сек на чтение
```

**На интервью:** Не нужна точность до байта. Нужно показать, что ты **умеешь оценивать порядок** — терабайт или гигабайт, тысяча RPS или миллион.

### Шаг 3: High-Level Design

```
Client → DNS → Load Balancer → API Gateway
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              Write Service   Read Service    Analytics Service
                    │               │               │
                    ▼               ▼               ▼
              Key Generator   Cache (Redis)    Kafka → ClickHouse
                    │               │
                    ▼               ▼
                Database      Database (replica)
```

**Объяснение компонентов:**
*   **Load Balancer** — распределяет трафик между серверами (Nginx / AWS ALB).
*   **Write Service** — принимает длинный URL, генерирует короткий, сохраняет.
*   **Read Service** — по короткому URL отдаёт redirect (HTTP 301/302).
*   **Key Generator** — генерирует уникальные короткие ключи.
*   **Cache (Redis)** — кэш горячих ссылок (80% трафика = 20% ссылок, закон Парето).
*   **Analytics** — Kafka собирает клики, ClickHouse агрегирует статистику.

### Шаг 4: Deep Dive — ключевые решения

#### 4a. Генерация коротких ключей

    +----------------------------------------+----------------------------------+----------------------------------------+
    | Подход                                 | Плюсы                            | Минусы                                 |
    +----------------------------------------+----------------------------------+----------------------------------------+
    | MD5/SHA256 → Base62 (первые 7 симв.)   | Прост                            | Коллизии (два URL → один хэш)          |
    | Auto-increment ID → Base62             | Нет коллизий, предсказуемый      | Утечка информации, SPOF                |
    | Pre-generated Key Service (KGS)        | Нет коллизий, быстро, масштаб.   | Дополнительный сервис                  |
    +----------------------------------------+----------------------------------+----------------------------------------+

**Лучший вариант для нашего случая:** KGS — заранее генерируем N миллионов ключей, складываем в отдельную таблицу, при записи берём следующий свободный.

```
7 символов Base62 = 62^7 ≈ 3.5 трлн уникальных ключей — хватит на десятки лет
```

#### 4b. Выбор базы данных

*   **Read-heavy (120K RPS)** → нужны реплики для чтения.
*   **Простая модель данных** (shortKey → longURL + metadata) → не нужны JOIN-ы.
*   **Огромный объём (90 TB)** → нужен горизонтальный шардинг.

**Решение:** NoSQL (DynamoDB / Cassandra) — горизонтальное масштабирование из коробки.
**Альтернатива:** PostgreSQL + шардинг (Citus) — если команда привыкла к SQL.

**Trade-off, который надо озвучить:** "NoSQL даёт eventual consistency — пользователь может не увидеть свою ссылку 100ms после создания. Для URL-shortener это приемлемо."

#### 4c. Кэширование

*   **Стратегия:** Cache-aside (Lazy Loading).
*   **Eviction policy:** LRU (Least Recently Used).
*   **TTL:** 24 часа для горячих ссылок.
*   **Размер кэша:** Если 20% ссылок генерируют 80% трафика → кэшируем 20% от дневных чтений.

```
120K RPS × 86400 сек/день = ~10B запросов/день
20% уникальных ссылок × 500B ≈ ~200 GB кэша в Redis
```

### Шаг 5: Масштабирование и отказоустойчивость

*   **Database Sharding:** По первому символу ключа (consistent hashing) → равномерное распределение.
*   **Read Replicas:** 3-5 реплик для чтения, мастер только для записи.
*   **Cache Cluster:** Redis Cluster с 3+ нодами.
*   **Rate Limiting:** На API Gateway — не больше 100 сокращений/мин на пользователя.
*   **Если Redis упадёт?** — Трафик пойдёт в БД. Latency вырастет, но сервис не ляжет. Автоматический failover на реплику Redis.
*   **Если один шард БД упадёт?** — Реплика этого шарда станет мастером (автоматический failover).

## 3. Ошибки, которые убивают System Design интервью

### ❌ Ошибка 1: Нырнуть в код / детали сразу
> "Я бы использовал PostgreSQL с таблицей urls, поле id serial primary key..."

**Почему плохо:** Ты ещё не знаешь масштаб. Может, тебе нужен NoSQL на 100TB. Сначала — требования и расчёты.

### ❌ Ошибка 2: Молчать
> *Рисует 3 минуты молча*

**Почему плохо:** Интервьюер не видит ход мыслей. А оценивают именно мышление, не результат.

**Что делать:** Думай вслух. "Я сейчас думаю, стоит ли разделить read и write сервисы... Учитывая, что у нас 100:1 чтение к записи — да, имеет смысл масштабировать их отдельно."

### ❌ Ошибка 3: Не обсуждать trade-offs
> "Я выбрал MongoDB."

**Почему плохо:** *Почему* MongoDB? Чем она лучше PostgreSQL для *этой конкретной* задачи?

**Формула:** "Я выбираю X **потому что** [причина], **trade-off** в том, что [минус], но это **приемлемо** потому что [обоснование]."

### ❌ Ошибка 4: Забыть про отказоустойчивость
> *Нарисовал красивую схему, но с одной БД*

**Почему плохо:** Одна нода = SPOF (Single Point of Failure). Интервьюер обязательно спросит: "Что если эта база упадёт?"

### ❌ Ошибка 5: Перфекционизм
> "Подождите, я ещё не нарисовал мониторинг, логирование, алертинг..."

**Почему плохо:** 45 минут — мало. Фокусируйся на ядре системы. Мониторинг упомяни одной фразой: "Здесь я бы добавил Prometheus + Grafana для метрик."

## 4. Шпаргалка: компоненты и когда их использовать

### Хранение данных

    +---------------+----------------------------------------+---------------------------+
    | Технология     | Когда использовать                    | Пример                    |
    +---------------+----------------------------------------+---------------------------+
    | PostgreSQL    | Сложные связи, транзакции, ACID       | Банк, e-commerce (заказы) |

    +------------+----------------------------------------+----------------------------------+

    +----------------+------------------------------------+----------------------------------------+
    | Паттерн        | Что делает                         | Когда                                   |
    +----------------+------------------------------------+----------------------------------------+
    | Load Balancer  | Распределяет запросы               | Всегда, с первого дня                   |
    | Read Replicas  | Копии БД для чтения                | Read-heavy нагрузка                     |
    | Sharding       | Горизонтальное разделение данных   | Данные не помещаются в одну ноду        |
    | CDN            | Раздаёт статику ближе к юзеру      | Медиа, статика, глобальные пользователи |
    | Cache (Redis)  | Снижает нагрузку на БД             | Горячие данные, частые запросы          |

## 5. Топ-10 задач System Design для Junior/Middle

Для каждой задачи — ключевой фокус, который ждёт интервьюер:

### Уровень 1 (начни с этих)
1. **URL Shortener (bit.ly)** — Key generation, read-heavy, кэширование
2. **Pastebin** — Похож на URL Shortener, но + хранение текста (S3)
3. **Rate Limiter** — Token Bucket / Sliding Window, Redis counters

### Уровень 2 (основные)
4. **Twitter / Instagram Feed** — Fan-out (push vs pull), timeline service, кэш ленты
5. **Chat System (WhatsApp)** — WebSockets, message queue, online status, delivery receipts
6. **Notification System** — Priority queue, multiple channels (push, email, SMS), retry logic

### Уровень 3 (продвинутые)
7. **YouTube / Netflix** — Video chunking, CDN, adaptive bitrate (HLS/DASH), upload pipeline
8. **Uber / Grab** — Geohashing, matching service, real-time location tracking
9. **Google Drive / Dropbox** — File sync, chunking, conflict resolution, deduplication
10. **Search Autocomplete** — Trie data structure, ranking, pre-computation

## 6. Мини-словарь (термины, которые надо знать)

    +---------------------+------------------------------------------------------------------+------------------------------------------+
    | Термин              | Что значит                                                        | Пример на пальцах                        |
    +---------------------+------------------------------------------------------------------+------------------------------------------+
    | CAP Theorem         | Из C, A, P можно гарантировать только два                        | MongoDB = CP, Cassandra = AP              |
    | Eventual Consistency| Данные когда-нибудь станут одинаковыми на всех нодах             | Лайк: 100 → 99 → 101 у обоих              |
    | SPOF                | Single Point of Failure — падение = падение всего                 | Одна база без реплик                     |
    | Horizontal Scaling  | Добавляем больше машин                                           | 10 серверов вместо одного                 |
    | Vertical Scaling    | Делаем машину мощнее                                             | Больше RAM, CPU                           |
    | Idempotency         | Повторный запрос даёт тот же результат                            | Двойной клик "Оплатить" не списывает 2х  |
    | Fan-out             | Один запрос порождает много действий                              | Пост → в ленте 1000 подписчиков          |
    | Consistent Hashing  | Распределение по нодам с минимальной перестройкой при добавлении  | Шардинг БД, кэш                          |
    | Back Pressure       | Система говорит "перегружена, подожди"                            | Rate limiting, очереди                   |
    | SLA/SLO/SLI         | Agreement / Objective / Indicator                                 | 99.9% uptime, latency < 200ms, замер     |
    +---------------------+------------------------------------------------------------------+------------------------------------------+

## Итого: формула успеха на System Design

```
Хороший ответ = Правильные вопросы + Расчёт нагрузки + Обоснованные решения + Trade-offs вслух
```

Интервьюеру неважно, какую именно базу ты выбрал. Ему важно **почему** ты её выбрал, **что** ты при этом теряешь, и **как** будешь масштабироваться, когда пользователей станет в 10 раз больше.
