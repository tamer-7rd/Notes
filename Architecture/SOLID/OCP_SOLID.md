# OCP (Open/Closed Principle) — для Junior

> "Программные сущности (классы, модули, функции и т.д.) должны быть открыты для расширения, но закрыты для модификации."

## 🎯 Что это значит простыми словами?

**"Код открыт для расширения, но закрыт для модификации"**

Перевод: когда нужно добавить новую фичу, ты **создаёшь новый код**, а не **меняешь старый**.



---

## ❌ Проблема: Почему это важно?

Представь, ты пишешь интернет-магазин. Нужно считать стоимость доставки.

### Плохой код (нарушение OCP):

```python
# delivery.py
def calculate_delivery(delivery_type):
    if delivery_type == "standard":
        return 100
    elif delivery_type == "express":
        return 500
    # Завтра заказчик просит добавить "drone" доставку
    # Ты лезешь СЮДА и дописываешь:
    elif delivery_type == "drone":
        return 1000
    # Потом просят "overnight" — опять лезешь сюда
    # Потом просят "pickup" — опять сюда
    # Каждый раз рискуешь сломать то, что уже работает!
```

**Проблема:** каждый раз, когда нужна новая доставка, ты **меняешь** эту функцию. Риск сломать старое.

---

## ✅ Решение: Как сделать правильно?

### Хороший код (соблюдение OCP):

```python
# 1. Создаём "контракт" (интерфейс) — это правило для всех доставок
class Delivery:
    def get_price(self):
        raise NotImplementedError("Каждая доставка должна уметь считать цену")

# 2. Каждая доставка — отдельный класс
class StandardDelivery(Delivery):
    def get_price(self):
        return 100

class ExpressDelivery(Delivery):
    def get_price(self):
        return 500

# 3. Нужна новая доставка? Просто создаём НОВЫЙ класс!
class DroneDelivery(Delivery):
    def get_price(self):
        return 1000

# 4. Функция расчета НЕ МЕНЯЕТСЯ больше никогда!
def calculate_delivery(delivery: Delivery):
    return delivery.get_price()

# Использование:
standard = StandardDelivery()
print(calculate_delivery(standard))  # 100

drone = DroneDelivery()
print(calculate_delivery(drone))  # 1000
```

**Преимущество:** чтобы добавить новую доставку, ты создаёшь **новый файл** с новым классом. Старый код не трогаешь → ничего не сломается.

## 🔍 Как понять, что ты нарушаешь OCP?

**Сигнал:** видишь длинный `if-elif-elif` или `switch-case`? Это часто нарушение OCP.

```python
# ❌ Плохо
def process_payment(method):
    if method == "paypal":
        # код PayPal
    elif method == "stripe":
        # код Stripe
    elif method == "crypto":
        # код Crypto
    # Каждый раз дописываешь сюда...

# ✅ Хорошо
class PaymentMethod:
    def pay(self, amount):
        raise NotImplementedError

class PayPal(PaymentMethod):
    def pay(self, amount):
        # код PayPal

class Stripe(PaymentMethod):
    def pay(self, amount):
        # код Stripe

def process_payment(payment: PaymentMethod, amount):
    payment.pay(amount)  # Этот код больше не меняется!
```

## 📋 Что такое "Контракт" (Интерфейс / Порт)?

**Контракт** (или **Порт**, или **Интерфейс**) — это договор: "У всех доставок есть метод `get_price()`".

В Python это абстрактный класс или просто соглашение.

**Важно:** "Порт", "Контракт" и "Интерфейс" — это **одно и то же**. Просто разные названия:
- **Контракт** — подчёркивает "договор" между классами
- **Порт** — подчёркивает "точку подключения" (как USB-порт, куда можно подключить разные устройства)
- **Интерфейс** — технический термин из программирования

```python
# Это КОНТРАКТ/ПОРТ/ИНТЕРФЕЙС — мы договорились, что у всех доставок есть get_price()
class Delivery:
    def get_price(self):
        raise NotImplementedError

# Все эти классы СОБЛЮДАЮТ контракт
class StandardDelivery(Delivery):
    def get_price(self):  # ← Обязательно должен быть этот метод
        return 100

class ExpressDelivery(Delivery):
    def get_price(self):  # ← И здесь тоже
        return 500
```

**Зачем:** если функция `calculate_delivery()` знает только про контракт (что есть `get_price()`), она может работать с **любой** доставкой, не зная деталей. Это и есть "порт" — место, куда можно "подключить" любую реализацию.

## 🔌 Что такое "Адаптер"?

**Адаптер** — это "переходник" для старого или чужого кода.

### Пример проблемы:

```python
# У тебя есть СТАРАЯ библиотека (ты её не можешь менять)
class OldLogger:
    def write_to_disk(self, message):
        print(f"Запись на диск: {message}")

# А в твоём проекте все используют новый интерфейс
class Logger:
    def log(self, message):
        raise NotImplementedError

# Как соединить старое и новое? → Адаптер!
class OldLoggerAdapter(Logger):
    def __init__(self):
        self.old_logger = OldLogger()  # Используем старую библиотеку
    
    def log(self, message):
        # Переводим вызов log() в write_to_disk()
        self.old_logger.write_to_disk(message)

# Теперь старый логгер работает как новый!
logger = OldLoggerAdapter()
logger.log("Привет")  # Внутри вызовется write_to_disk()
```

**Зачем:** чтобы не переписывать весь проект, когда подключаешь чужую библиотеку.

## 🎨 Что такое "Декоратор"?

**Декоратор** — это "обёртка", которая добавляет фичу, не меняя основной код.

### Пример:

```python
# Базовый сервис отправки уведомлений
class NotificationService:
    def send(self, message):
        print(f"Отправка: {message}")

# Декоратор добавляет ЛОГИРОВАНИЕ
class LoggingDecorator(NotificationService):
    def __init__(self, service):
        self.service = service  # Оборачиваем оригинальный сервис
    
    def send(self, message):
        print(f"[LOG] Попытка отправить: {message}")
        self.service.send(message)  # Вызываем оригинал
        print(f"[LOG] Отправлено успешно")

# Декоратор добавляет ПОВТОРЫ при ошибке
class RetryDecorator(NotificationService):
    def __init__(self, service):
        self.service = service
    
    def send(self, message):
        for i in range(3):
            try:
                self.service.send(message)
                return
            except:
                print(f"Попытка {i+1} не удалась, повторяю...")

# Использование:
base_service = NotificationService()
# Оборачиваем в декораторы
service = RetryDecorator(LoggingDecorator(base_service))
service.send("Привет!")
# Вывод:
# [LOG] Попытка отправить: Привет!
# Отправка: Привет!
# [LOG] Отправлено успешно
```

**Зачем:** чтобы добавить логирование/кэш/ретраи **ко всем** сервисам сразу, не меняя каждый класс.

## 🎮 Что такое "Контроллер"?

**Контроллер** — это код, который "управляет процессом", но не знает деталей.

### Пример:

```python
# Контроллер заказа — он НЕ ЗНАЕТ, какая именно оплата используется
class OrderController:
    def __init__(self, payment_service):  # Получаем "любую оплату"
        self.payment = payment_service
    
    def process_order(self, amount):
        print("Обработка заказа...")
        self.payment.pay(amount)  # Просто вызываем pay()
        print("Заказ обработан!")

# Разные способы оплаты
class PayPal:
    def pay(self, amount):
        print(f"PayPal: списано {amount}")

class Stripe:
    def pay(self, amount):
        print(f"Stripe: списано {amount}")

# Контроллер работает с ЛЮБОЙ оплатой!
paypal = PayPal()
controller1 = OrderController(paypal)
controller1.process_order(100)

stripe = Stripe()
controller2 = OrderController(stripe)
controller2.process_order(200)
```

**Зачем:** если завтра нужно заменить PayPal на Stripe, контроллер **не меняется**. Меняешь только то, что передаёшь в конструктор.

## 🛠 Зачем здесь Адаптеры, Декораторы и Контроллеры?

Это **инструменты**, с помощью которых ты соблюдаешь OCP на практике.

1.  **Адаптер** — чтобы подключить **чужой код** (библиотеку) без переписывания своей системы. Ты не меняешь свой код, а пишешь "переходник".
2.  **Декоратор** — чтобы **добавить фичу** (например, логирование) без влезания в рабочий класс. Ты не правишь класс, а "оборачиваешь" его.
3.  **Контроллер** — пример того, **как пользоваться** этим всем. Если он зависит от интерфейса, ему можно подсунуть что угодно (Адаптер, Декоратор), и он продолжит работать без изменений.

---

## 🎯 Итоговая схема (как это всё работает вместе):

```
┌─────────────────┐
│  Контроллер     │  ← Не знает деталей, работает с "контрактом"
│  (OrderController)│
└────────┬────────┘
         │ использует
         ▼
┌─────────────────┐
│   Контракт      │  ← Правило: "у всех есть метод pay()"
│  (PaymentMethod)│
└────────┬────────┘
         │ реализуют
    ┌────┴────┬──────────┐
    ▼         ▼          ▼
┌──────┐  ┌──────┐  ┌────────┐
│PayPal│  │Stripe│  │Crypto  │  ← Конкретные реализации
└──────┘  └──────┘  └────────┘
```

**Нужна новая оплата?** Создаёшь новый класс (например, `BankTransfer`), который реализует контракт. Контроллер продолжает работать без изменений.

## ✅ Чеклист: Когда применять OCP?

Задай себе:
1. **Будут ли добавляться новые типы?** (новые доставки, оплаты, уведомления?)
2. **Если да, придётся ли менять много кода?**
3. **Нужны ли разные варианты?** (тестовая/реальная оплата?)

Если **да** хотя бы на один → используй OCP (интерфейсы + классы).

Если **нет** на все → делай просто, не усложняй (YAGNI).

---

## 🎓 Главное для Junior:

1. **Видишь длинный `if-elif`?** → Подумай про OCP.
2. **Нужно добавить новый тип?** → Создай новый класс, не меняй старый.
3. **Контракт (интерфейс)** — это правило, которое все должны соблюдать.
4. **Адаптер** — для подключения чужого кода.
5. **Декоратор** — для добавления фич (логирование, кэш) без изменения основного кода.
6. **Контроллер** — не должен знать детали, только контракт.

**Помни:** OCP не значит "никогда не менять код". Это значит: **меняй так, чтобы в будущем менять было не нужно.**
