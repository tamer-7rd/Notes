# D — Dependency Inversion Principle (Принцип инверсии зависимостей)
## Суть принципа
DIP — это последний принцип из SOLID. Он звучит так:  
Модули верхнего уровня не должны зависеть от модулей нижнего уровня. И те, и другие должны зависеть от абстракций. Абстракции не 
должны зависеть от деталей. Детали должны зависеть от абстракций.
## 🎯 Что это значит простыми словами?
Простыми словами:
- Главная программа (высокоуровневый модуль) не должна напрямую привязываться к конкретным реализациям (низкоуровневым деталям).
- Нужно строить зависимость через интерфейсы или абстрактные классы.

**"Завись от абстракций, а не от деталей"**

Перевод:
1. Твой код не должен зависеть от конкретных классов (MySQL, GoogleDrive, AWS).
2. Он должен зависеть от **интерфейсов** (База Данных, Хранилище, Облако).

**Главная фишка:** ты можешь подменить базу данных, API или диск, не переписывая основной код приложения.

---

## Почему это важно?

Если верхний уровень зависит от деталей, любое изменение в этих деталях ломает всю систему.  
DIP делает код:
- более гибким (легко заменить реализацию),
- более тестируемым (можно подменять зависимости моками),
- более устойчивым к изменениям.

## 🔌 Лучшая аналогия: Розетка
Представь, ты втыкаешь зарядку ноутбука в стену.
*   **Розетка** — это **абстракция (интерфейс)**. Стандартная дырка с напряжением.
*   **Вилка ноутбука** — зависит от **интерфейса розетки**, а не от того, откуда там ток (ТЭЦ, АЭС, ветряк).
*   **ТЭЦ (источник тока)** — это **деталь реализации**.

**Соблюдение DIP:** Ты можешь поменять ТЭЦ на солнечную батарею, но если розетка та же — твой ноутбук продолжит работать. Тебе не надо перепаивать ноутбук под каждую электростанцию.

## ❌ Проблема: Жёсткая привязка (Нарушение DIP)

Представь приложение, которое сохраняет данные в MySQL.

```python
# Низкоуровневая деталь (Конкретная БД)
class MySQLDatabase:
    def connect(self):
        print("Подключение к MySQL...")
    
    def save(self, data):
        print(f"Сохраняю {data} в MySQL")

# Высокоуровневый модуль (Наше приложение)
class Application:
    def __init__(self):
        # ❌ ОШИБКА: Мы прибили гвоздями конкретную базу!
        self.db = MySQLDatabase()
    
    def save_user(self, user):
        self.db.connect()
        self.db.save(user)
```

**Почему это плохо?**
Если завтра босс скажет: *"Переезжаем на PostgreSQL"* или *"Надо тестить без реальной базы"*, тебе придётся **переписывать класс `Application`**.
Верхний уровень (`Application`) зависит от нижнего (`MySQLDatabase`). Это неправильно.

---

## ✅ Решение: Инверсия зависимостей

Мы ставим между ними "Прокладку" (Интерфейс). Теперь и Приложение, и База зависят от этого Интерфейса.

```python
from abc import ABC, abstractmethod

# 1. Абстракция (Интерфейс / Розетка)
class Database(ABC):
    @abstractmethod
    def connect(self): pass
    
    @abstractmethod
    def save(self, data): pass

# 2. Детали (Конкретные реализации / Вилки)
class MySQLDatabase(Database):
    def connect(self): print("MySQL connect...")
    def save(self, data): print(f"MySQL save: {data}")

class PostgreSQLDatabase(Database):
    def connect(self): print("Postgres connect...")
    def save(self, data): print(f"Postgres save: {data}")

# 3. Приложение (Зависит от Абстракции)
class Application:
    # ✅ Мы принимаем ЛЮБУЮ базу, которая соответствует интерфейсу
    def __init__(self, db: Database):
        self.db = db
    
    def save_user(self, user):
        self.db.connect()
        self.db.save(user)

# Использование:
# Хотим MySQL? Пожалуйста.
mysql_app = Application(MySQLDatabase())
mysql_app.save_user("User1")

# Хотим Postgres? Легко! Код Application НЕ МЕНЯЕТСЯ.
pg_app = Application(PostgreSQLDatabase())
pg_app.save_user("User2")
```

## 🔍 Жизненный пример: Уведомления

### ❌ Плохо (Без DIP):
```python
class NotificationService:
    def __init__(self):
        self.email = EmailSender() # Привязались к Email
    
    def notify(self, msg):
        self.email.send(msg)
```
*Захотели добавить SMS? Придётся переписывать `NotificationService`.*

### ✅ Хорошо (С DIP):
```python
class NotificationService:
    def __init__(self, sender: Sender): # Зависим от интерфейса Sender
        self.sender = sender
    
    def notify(self, msg):
        self.sender.send(msg)

# Можем подсунуть что угодно:
service = NotificationService(EmailSender())
service = NotificationService(SMSSender())
service = NotificationService(TelegramSender())
```

## 🎯 Как понять, что ты нарушаешь DIP?

1. Ты используешь ключевое слово `new` (или создание класса `MyClass()`) прямо внутри другого класса.
   *   *Вместо `self.db = MySQL()` лучше передавать `db` в конструктор (`__init__`).*
2. Твой код сложно тестировать. (Нельзя подсунуть фейковую базу данных).
3. Чтобы поменять базу данных/API/библиотеку, тебе приходится править бизнес-логику.

---

## 🎓 Главное для Junior:

1. **Модули верхнего уровня** (бизнес-логика) не должны зависеть от **модулей нижнего уровня** (базы, API, диски).
2. Оба должны зависеть от **абстракций** (интерфейсов).
3. **Dependency Injection (Внедрение зависимостей)** — это когда мы передаем нужные объекты (базу, логгер) в конструктор, а не создаем их внутри. Это главный способ соблюдать DIP.

**Запомни:** Сначала придумай "Розетку" (Интерфейс), а потом уже паяй к ней "Провода" (Реализацию).
