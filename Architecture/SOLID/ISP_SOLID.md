# Конспект: I — Interface Segregation Principle (Принцип разделения интерфейсов)

## 1. Определение
- **Суть:** Клиенты не должны зависеть от интерфейсов, которые они не используют.  
- Лучше много маленьких интерфейсов, чем один «толстый».  
- Этот принцип защищает от избыточных обязанностей и пустых реализаций.
## 🎯 Что это значит простыми словами?
**"Не заставляй класс реализовывать то, что ему не нужно"**

## 2. Интерфейс и Клиент
- **Интерфейс** — это набор публичных методов/свойств, которые объект предоставляет внешнему миру. Это *контракт*: «вот что я умею».  
- **Клиент** — это любой код, который этим интерфейсом пользуется. Клиенту всё равно, как методы реализованы внутри, ему важно только, что их можно вызвать.  

Перевод: лучше создать 3 маленьких интерфейса (контракта), чем 1 огромный, в котором свалено всё в кучу. Если ты видишь, что в методе стоит `pass` или `raise NotImplementedError` просто потому, что "интерфейс требует" — это нарушение ISP.

## ❌ Проблема: Толстые интерфейсы

Представь, ты делаешь систему для управления устройствами в офисе.

### Плохой код (Нарушение ISP):

```python
# Огромный интерфейс "Всё-в-одном"
class SmartDevice:
    def print(self):
        raise NotImplementedError
    def fax(self):
        raise NotImplementedError
    def scan(self):
        raise NotImplementedError

# Реализация: МФУ (умеет всё)
class AllInOnePrinter(SmartDevice):
    def print(self):
        print("Печатаю...")
    def fax(self):
        print("Отправляю факс...")
    def scan(self):
        print("Сканирую...")

# Реализация: Обычный принтер (не умеет сканировать и факс)
class SimplePrinter(SmartDevice):
    def print(self):
        print("Печатаю...")
    
    # ❌ Приходится писать пустые методы или выбрасывать ошибки!
    def fax(self):
        raise Exception("Я не умею отправлять факс!")
    
    def scan(self):
        raise Exception("Я не умею сканировать!")
```

**Проблема:** `SimplePrinter` **вынужден** реализовывать методы `fax` и `scan`, хотя они ему не нужны. Это мусорный код. Если интерфейс `SmartDevice` изменится (добавят `copy`), придётся менять и `SimplePrinter`, хотя это его не касается.

## ✅ Решение: Разделяй интерфейсы

### Хороший код (Соблюдение ISP):

```python
# Разбили на маленькие интерфейсы по смыслу
class Printer:
    def print(self):
        raise NotImplementedError

class Scanner:
    def scan(self):
        raise NotImplementedError

class Fax:
    def fax(self):
        raise NotImplementedError

# МФУ реализует все 3 интерфейса
class AllInOnePrinter(Printer, Scanner, Fax):
    def print(self):
        print("Печатаю...")
    def scan(self):
        print("Сканирую...")
    def fax(self):
        print("Факс...")

# Обычный принтер реализует ТОЛЬКО то, что ему нужно
class SimplePrinter(Printer):
    def print(self):
        print("Печатаю...")
    # И никаких лишних методов fax/scan!
```

**Преимущество:** Классы чистые, без мусора. Изменения в `Scanner` никак не сломают `SimplePrinter`.

## 🔍 Еще пример: Управление юзером (Admin vs User)

### ❌ Плохо (Один интерфейс на всех):

```python
class IUserActions:
    def view_content(self): pass
    def edit_content(self): pass  # Обычный юзер не должен это уметь!
    def delete_user(self): pass   # Тем более это!

class RegularUser(IUserActions):
    def view_content(self):
        print("Смотрю контент")
    
    def edit_content(self):
        raise PermissionError("Нельзя!") # ❌ Костыль
        
    def delete_user(self):
        raise PermissionError("Нельзя!") # ❌ Костыль
```

### ✅ Хорошо (Разделение прав):

```python
# Интерфейс для обычного читателя
class IViewer:
    def view_content(self): pass

# Интерфейс для редактора
class IEditor:
    def edit_content(self): pass

# Интерфейс для админа
class IAdmin:
    def delete_user(self): pass

# Теперь собираем классы как конструктор:
class RegularUser(IViewer):
    def view_content(self): print("Смотрю")

class Moderator(IViewer, IEditor):
    def view_content(self): print("Смотрю")
    def edit_content(self): print("Редактирую")

class SuperAdmin(IViewer, IEditor, IAdmin):
    # Умеет всё
    pass
```

## 🎯 Как понять, что ты нарушаешь ISP?

Задай себе вопросы:
1. **Есть ли в моем классе пустые методы (`pass`)?**
2. **Есть ли методы, которые выбрасывают ошибку "Я это не поддерживаю"?**
3. **Заставляю ли я клиента зависеть от методов, которые он не вызывает?**

Если **да** → разбей интерфейс на части.

---

## 🎓 Главное для Junior:

1. **Интерфейс должен быть узким и специализированным.** Лучше 5 интерфейсов по 2 метода, чем 1 интерфейс с 10 методами.
2. **Классы не должны тащить за собой "мертвый груз"** ненужных методов.
3. **ISP помогает соблюдать SRP** (Принцип единственной ответственности): каждый интерфейс отвечает за что-то одно.

## 7. Главное, что вынести
- Интерфейс = контракт («что объект умеет»).  
- Клиент = тот, кто этот контракт использует.  
- Принцип ISP говорит: не заставляй клиентов зависеть от лишних методов.  
- Маленькие интерфейсы → простые реализации → меньше багов.  
**Запомни:** Клиент (тот, кто пользуется классом) должен видеть только то, что ему реально нужно.
