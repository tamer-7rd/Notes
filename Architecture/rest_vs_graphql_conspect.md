# REST vs GraphQL — для Junior

## 🎯 Что это простыми словами?

**REST** и **GraphQL** — это два способа построения API для общения любых клиентов и серверов (не только фронта и бэка).

**Разница:**
- **REST** = много разных URL-эндпоинтов, каждый для одного ресурса (`/users`, `/posts`).
- **GraphQL** = один эндпоинт `/graphql`, клиент сам выбирает, какие поля нужны.

**Аналогия:**
- **REST** = меню в ресторане: заказываешь блюдо целиком (салат, суп, второе).
- **GraphQL** = шведский стол: выбираешь только то, что хочешь (только помидоры из салата, только бульон из супа).

---

## 🔹 Что такое REST?

**REST (Representational State Transfer)** = архитектурный стиль построения API вокруг ресурсов.

### Структура REST:

API строится вокруг **ресурсов** (`users`, `posts`, `articles`).

**Примеры эндпоинтов:**
```
GET    /users         → получить список пользователей
GET    /users/5       → получить пользователя №5
POST   /users         → создать пользователя
PUT    /users/5       → обновить пользователя
DELETE /users/5       → удалить пользователя
```

### Плюсы REST:
✅ Легко начать — понятная структура  
✅ Читаемые URL — сразу видно, что запрашиваешь  
✅ Отлично кэшируется через CDN, браузер, Vercel  
✅ Подходит для CRUD-приложений и микросервисов  

### Минусы REST:
❌ **Overfetching** — иногда приходит слишком много данных  
❌ **Underfetching** — иногда нужно сделать несколько запросов вместо одного  

---

## 🔹 Что такое GraphQL?

**GraphQL** = язык запросов и система выполнения запросов. Один эндпоинт `/graphql`, клиент сам указывает, какие поля нужны.

### Пример запроса GraphQL:

```graphql
query {
  user(id: 5) {
    name
    avatar
    posts(limit: 2) {
      title
      likes
    }
  }
}
```

**Что происходит:** Клиент говорит "Дай мне пользователя №5, но только имя, аватар и его 2 последних поста с заголовком и лайками".

### Плюсы GraphQL:
✅ Клиент получает только нужные данные (нет overfetching)  
✅ Один запрос вместо нескольких (нет underfetching)  
✅ Гибкая структура запросов  
✅ Типобезопасность (схема определяет типы)  

### Минусы GraphQL:
❌ Сложнее начать — нужна схема, резолверы  
❌ Сложнее кэшировать (нет стандартных HTTP-кэшей)  
❌ Может быть избыточным для простых проектов  

---

## ❌ Проблемы REST

### 1. Overfetching (Получение лишних данных)

**Пример:**
```javascript
// Запрос: нужны только имя и email пользователя
GET /users/5

// Ответ: приходит ВСЁ про пользователя
{
  "id": 5,
  "name": "Tamerlan",
  "email": "tamerlan@example.com",
  "bio": "Very long bio...",
  "avatar": "url...",
  "createdAt": "2024-01-01",
  "lastLogin": "2024-12-01",
  "settings": {...},
  "posts": [...],
  // ... ещё 20 полей
}
```

**Проблема:** Передаётся много данных, которые не нужны клиенту.

### 2. Underfetching (Недостаточно данных)

**Пример:**
```javascript
// Нужны: статья + автор + комментарии

// Запрос 1: получаем статью
GET /articles/42
// Ответ: { id: 42, title: "...", authorId: 5 }

// Запрос 2: получаем автора
GET /users/5
// Ответ: { id: 5, name: "...", avatar: "..." }

// Запрос 3: получаем комментарии
GET /articles/42/comments
// Ответ: [{ id: 1, text: "...", userId: 3 }, ...]

// Запрос 4: получаем авторов комментариев
GET /users/3
GET /users/7
// ...
```

**Проблема:** Нужно делать несколько запросов вместо одного.

---

## ✅ Решение: GraphQL

GraphQL решает обе проблемы одним запросом:

```graphql
query {
  article(id: 42) {
    title
    author {
      name
      avatar
    }
    comments(limit: 5) {
      text
      author {
        name
      }
    }
  }
}
```

**Результат:** Один запрос, только нужные поля, всё в одном ответе.

## 🧩 Архитектура запросов

### REST — по ресурсам:

```
[Client (React/Next.js)]
        |
        |  GET /articles?limit=10&page=1
        v
[API Gateway / Load Balancer]
        |
        v
[REST Controller]
        |
        v
[Service Layer]
        |
        v
[Repository]
        |
        v
[Database]
```

**При underfetching:** Делается несколько запросов:
```
GET /articles/42
GET /users/5          ← дополнительный запрос
GET /articles/42/comments
GET /users/3          ← ещё запросы
GET /users/7
```

### GraphQL — один запрос:

```
[Client + Apollo Client]
        |
        |  POST /graphql
        |  { query: "{ article(id:42){ title author{name} } }" }
        v
[GraphQL Server]
        |
        v
[Resolvers] ──→ [Service] ──→ [Repository] ──→ [Database]
        |
        └── DataLoader (батчинг запросов)
```

**Преимущество:** Один запрос, GraphQL сам собирает данные из разных источников.

## 🎯 Когда использовать REST?

**Используй REST, если:**

- ✅ Проект только начинается (прототип, MVP).
- ✅ Простые ресурсы (`/users`, `/posts`, `/articles`).
- ✅ Нет сложных вложенных структур.
- ✅ Важна скорость разработки.
- ✅ Нужно кэширование через CDN/Vercel.

**Примеры:** Блог, интернет-магазин, новостной сайт.

---

## 🎯 Когда использовать GraphQL?

**Используй GraphQL, если:**

- ✅ Есть мобильное приложение (важно минимизировать трафик).
- ✅ Сложные вложенные структуры данных (автор → проекты → активности → фолловеры).
- ✅ Разные клиенты нуждаются в разных данных (веб, мобилка, админка).
- ✅ Частые проблемы с overfetching/underfetching в REST.
- ✅ Нужна гибкая фильтрация и выборка.

**Примеры:** Социальные сети, дашборды с множеством виджетов, мобильные приложения.

---

## 📋 Чек-лист: REST или GraphQL?

**Выбирай REST, если:**
- [ ] Проект только начинается?
- [ ] Простые ресурсы без сложных связей?
- [ ] Важна скорость разработки?
- [ ] Нужно кэширование через CDN?

**Выбирай GraphQL, если:**
- [ ] Есть мобильное приложение?
- [ ] Сложные вложенные структуры данных?
- [ ] Разные клиенты нуждаются в разных данных?
- [ ] Частые проблемы с overfetching/underfetching?

**Для Junior:** Начни с REST. Это проще и понятнее. GraphQL изучи позже, когда столкнёшься с его преимуществами на практике.

## 🚀 Стратегия развития API

### Этап 1: Начинаем с REST
```
REST API
├── Controller → Service → Repository
├── Простые эндпоинты (/users, /posts)
└── Быстро и понятно
```

### Этап 2: Добавляем GraphQL (опционально)
```
REST API (остаётся)
    +
GraphQL API (добавляется)
├── Можно использовать общие Service/Repository слои
└── Клиент выбирает: /api (REST) или /graphql
```

**Важно:** GraphQL можно добавить как второй слой поверх REST, не ломая существующую архитектуру, если REST построен грамотно (через Service/Repository слои).

---

## 🎓 Главное для Junior:

1. **REST** = много эндпоинтов, каждый для одного ресурса. Проще начать.
2. **GraphQL** = один эндпоинт, клиент выбирает поля. Гибче, но сложнее.
3. **REST проблемы:** Overfetching (лишние данные) и Underfetching (несколько запросов).
4. **GraphQL решает:** Один запрос, только нужные поля.
5. **Для начала:** Используй REST. GraphQL изучи позже, когда поймёшь его преимущества.

**Запомни:** REST — это "калашников" (просто и надёжно). GraphQL — это "дрон" (мощнее, но сложнее). Начинай с простого!
