# Adapter и Decorator — для Junior

Два паттерна, которые помогают соблюдать **OCP** (Open/Closed Principle). Они позволяют расширять функциональность без изменения существующего кода.

---

## 🏗️ Паттерн Adapter (Адаптер)

### 🎯 Что это?

**Адаптер** — это "переводчик" между несовместимыми интерфейсами. Он позволяет использовать чужой код (библиотеку, API) в своей системе без переписывания всего проекта.

**Аналогия:** Как переходник между вилкой и розеткой разного стандарта — адаптер позволяет соединить их.

---

### ❌ Проблема: Несовместимые интерфейсы

У тебя есть внешний API, который возвращает температуру в Фаренгейтах, а твоя система работает только с Цельсиями. Что делать?

**Вариант 1 (Плохо):** Переписать всю систему под Фаренгейты.
**Вариант 2 (Плохо):** Везде в коде писать `(temp_f - 32) * 5/9`.
**Вариант 3 (Хорошо):** Создать адаптер, который переводит "на лету".

---

### ✅ Решение: Адаптер

```python
# Внешний API (мы его не можем менять)
class ExternalWeatherAPI:
    def fetch_weather_data(self):
        return {'temp_f': 71.6, 'rh_percent': 75}  # Фаренгейты!

# Наш интерфейс (стандарт проекта)
class WeatherService:
    def get_temperature_celsius(self):
        raise NotImplementedError
    def get_humidity_percentage(self):
        raise NotImplementedError

# Адаптер — "переводчик"
class WeatherAdapter(WeatherService):
    def __init__(self, external_api: ExternalWeatherAPI):
        self._api = external_api

    def get_temperature_celsius(self):
        data = self._api.fetch_weather_data()
        # Переводим Фаренгейты в Цельсии
        return round((data['temp_f'] - 32) * 5 / 9, 1)

    def get_humidity_percentage(self):
        return self._api.fetch_weather_data()['rh_percent']

# Использование
def display_weather(service: WeatherService):
    print(f"Погода: {service.get_temperature_celsius()}°C, "
          f"Влажность: {service.get_humidity_percentage()}%")

# Теперь можем использовать внешний API через адаптер
api = ExternalWeatherAPI()
adapter = WeatherAdapter(api)
display_weather(adapter)  # ✅ Работает!
```

**Главная идея:** Адаптер **меняет интерфейс** объекта, не изменяя сам объект.

---

### Когда применять Adapter?

- ✅ Интеграция с внешними API или библиотеками.
- ✅ Работа с устаревшим кодом, который нельзя менять.
- ✅ Приведение чужого интерфейса к своему стандарту.

## 🎁 Паттерн Decorator (Декоратор)

### 🎯 Что это?

**Декоратор** — это "обёртка", которая добавляет новое поведение объекту, не меняя его код. Можно наслаивать несколько декораторов друг на друга.

**Аналогия:** Как украшения на ёлке: сама ёлка (объект) остаётся той же, но ты можешь добавлять на неё новые элементы, не переписывая дерево.

---

### ❌ Проблема: Нужно добавить логирование/кэш/проверки

Ты написал класс `EmailNotifier`, который отправляет письма. Теперь нужно:
1. Логировать каждую отправку.
2. Сжимать большие сообщения.
3. Кэшировать результаты.

**Вариант 1 (Плохо):** Лечь в класс `EmailNotifier` и дописать туда всё.
**Вариант 2 (Хорошо):** Обернуть в декораторы.

---

### ✅ Решение: Декораторы

```python
# Базовый интерфейс
class Notifier:
    def send(self, message: str):
        raise NotImplementedError

# Конкретная реализация
class EmailNotifier(Notifier):
    def send(self, message: str):
        print(f"ОТПРАВЛЕНО (Email): '{message}'")
        return True

# Базовый декоратор
class NotifierDecorator(Notifier):
    def __init__(self, notifier: Notifier):
        self._notifier = notifier

    def send(self, message: str):
        return self._notifier.send(message)

# Декоратор для логирования
class LoggingDecorator(NotifierDecorator):
    def send(self, message: str):
        print(f"[ЛОГ] Отправка: '{message[:20]}...'")
        result = super().send(message)
        print(f"[ЛОГ] Успех: {result}")
        return result

# Декоратор для сжатия
class CompressionDecorator(NotifierDecorator):
    def send(self, message: str):
        compressed_message = f"[{len(message)} байт сжато]"
        print(f"[СЖАТИЕ] Исходный размер: {len(message)}")
        return super().send(compressed_message)

# Использование: наслаиваем декораторы
base = EmailNotifier()
decorated = LoggingDecorator(CompressionDecorator(base))
decorated.send("Очень длинное уведомление о состоянии сервера.")

# Вывод:
# [ЛОГ] Отправка: 'Очень длинное уведомл...'
# [СЖАТИЕ] Исходный размер: 45
# ОТПРАВЛЕНО (Email): '[45 байт сжато]'
# [ЛОГ] Успех: True
```

**Главная идея:** Декоратор **расширяет поведение** объекта, сохраняя его интерфейс.

---

### Когда применять Decorator?

- ✅ Добавление логирования, кэширования, проверки прав.
- ✅ Модификация поведения во время выполнения программы.
- ✅ Когда нужно добавить фичу "поверх" существующего кода без его изменения.

---

## 🔑 Сравнение Adapter и Decorator

```
+----------------------+---------------------------+---------------------------+
| Характеристика       | Adapter                   | Decorator                 |
+----------------------+---------------------------+---------------------------+
| Цель                 | Преобразовать интерфейс   | Расширить поведение       |
+----------------------+---------------------------+---------------------------+
| Отношение            | Несовместимые интерфейсы  | Один и тот же интерфейс   |
+----------------------+---------------------------+---------------------------+
| Роль                 | «Переводчик»              | «Улучшатель»              |
+----------------------+---------------------------+---------------------------+
| Когда применять      | Интеграция с внешними     | Добавление функциональности|
|                      | системами                 |                           |
+----------------------+---------------------------+---------------------------+
```

## 🧱 Зачем декораторы, если можно просто вызвать функцию?

Иногда можно просто вызвать функцию внутри другой, но декоратор делает это **чище и безопаснее**.

### ❌ Плохо (Ручные проверки):

```python
def check_admin_access():
    if "admin" not in CURRENT_USER_ROLES:
        raise PermissionError("Access Denied")

def delete_critical_data(item_id):
    check_admin_access()  # Нужно помнить вызывать вручную
    # основная логика...

def update_critical_data(item_id):
    check_admin_access()  # Опять вручную...
    # основная логика...
```

**Проблема:** Легко забыть вызвать проверку. Код размазан.

### ✅ Хорошо (Декоратор):

```python
@requires_role("admin")
def delete_critical_data(item_id):
    # основная логика...

@requires_role("admin")
def update_critical_data(item_id):
    # основная логика...
```

**Преимущества:**
1. **Чистота** — сразу видно требование.
2. **DRY** — не нужно копировать проверку везде.
3. **Безопасность** — нельзя забыть вызвать проверку.
4. **Гибкость** — можно наслаивать:

```python
@cache_result
@requires_role("admin")
@check_login_status
def get_report(report_id):
    ...
```

## 📋 Чек-лист: Когда использовать?

**Adapter нужен, если:**
- [ ] Подключаешь внешнюю библиотеку/API с другим интерфейсом.
- [ ] Работаешь со старым кодом, который нельзя менять.
- [ ] Нужно привести чужой интерфейс к своему стандарту.

**Decorator нужен, если:**
- [ ] Нужно добавить логирование/кэш/проверки к нескольким классам.
- [ ] Хочешь расширить функциональность без изменения основного кода.
- [ ] Нужно комбинировать несколько "улучшений" (логирование + кэш + проверка).

---

## 💬 Итог

- **Adapter** решает проблему несовместимости интерфейсов (переводчик).
- **Decorator** решает задачу расширения поведения (улучшатель).
- Оба паттерна помогают соблюдать **OCP** (Open/Closed Principle): расширяем функциональность без изменения существующего кода.
