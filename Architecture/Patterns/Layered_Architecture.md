# Слоистая Архитектура (Layered Architecture)

Привет! Давай разберем одну из самых популярных архитектурных паттернов — **Слоистую Архитектуру** (Layered Architecture). Представь, что это слоеный пирог 🍰, где каждый слой имеет свой вкус и назначение, и смешивать их в кучу нельзя, иначе получится каша.

В классическом варианте (как в Domain-Driven Design) выделяют 4 основных слоя. Давай пройдемся по ним сверху вниз.

---

## 1. Presentation Layer (Слой Представления / UI)

📍 **Где находится:** На самом верху.
👀 **За что отвечает:** За взаимодействие с пользователем (или другой системой).

Это "лицо" твоего приложения. Здесь находятся контроллеры (в Web API), UI-компоненты (в Frontend), обработчики консольных команд.
Этот слой **ничего не знает о бизнес-логике**. Его задача — принять данные от пользователя, передать их вниз и показать ответ.

**Пример:**
- Кнопка "Купить" на сайте.
- REST Controller `POST /orders`.

---

## 2. Application Layer (Слой Приложения)

📍 **Где находится:** Под UI.
🤝 **За что отвечает:** Оркестрация (координация) действий.

Это "менеджер". Он знает, *что* нужно сделать, но не знает *как* именно работают правила бизнеса. Он получает команду от UI, собирает нужные инструменты (сервисы домена, репозитории) и говорит им работать.

**Важно:** Здесь не должно быть сложной бизнес-логики (проверок, расчетов). Только координация.

**Пример:**
- Сервис `OrderService`, метод `createOrder()`.
- Он вызывает: "Найти товар" -> "Проверить наличие" -> "Списать деньги" -> "Сохранить заказ".

---

## 3. Domain Layer (Доменный Слой)

📍 **Где находится:** В центре (или под Application).
❤️ **За что отвечает:** Бизнес-логика и правила. Сердце приложения.

Здесь живут твои Сущности (Entities), Объекты-значения (Value Objects) и Доменные сервисы. Этот слой содержит правила, которые делают твой бизнес бизнесом. Он **максимально изолирован** и не должен зависеть от базы данных или фреймворков. (Это рекомендация для СОВРЕМЕННОГО подхода (Clean/Onion).)

**Пример:**
- Сущность `Order`.
- Правило: "Нельзя оформить заказ, если сумма товаров меньше 500 рублей".
- Правило: "При отмене заказа статус меняется на Canceled".

---

## 4. Infrastructure Layer (Слой Инфраструктуры)

📍 **Где находится:** В самом низу (но технически обеспечивает работу всех).
🛠 **За что отвечает:** Работа с "железом" и внешним миром.

Здесь лежат реализации того, *как* мы храним данные или отправляем письма. Базы данных, файловые системы, сторонние API (Stripe, PayPal), логирование.

**Пример:**
- `SqlOrderRepository` (сохраняет заказ в PostgreSQL).
- `SmtpEmailService` (отправляет письмо через SMTP).

---

## 🔄 Главное правило: Направление зависимостей

В строгой слоистой архитектуре зависимости идут **только сверху вниз**.

1. **UI** знает про **Application**.
2. **Application** знает про **Domain**.
3. **Infrastructure** — тут есть нюанс (см. ниже).

---

## 🆚 Классическая vs Современная версия

**Layered Architecture — актуальная и современная!** Но есть два варианта её реализации:

### Вариант 1: Классическая (традиционная)

```
UI → Application → Domain → Infrastructure
                              ↑
                    Domain ЗАВИСИТ от Infrastructure
```

В классике **Domain может знать про Infrastructure**:
- Интерфейс `IOrderRepository` лежит в **Infrastructure**
- Domain импортирует его оттуда

**Проблема:** Domain привязан к инфраструктуре. Хочешь протестировать бизнес-логику — нужно поднимать БД или мокать.

### Вариант 2: Современная (Clean / Onion / Hexagonal)

```
Infrastructure → Application → Domain ← Infrastructure
                                 ↑
                    Все зависят ОТ Domain (к центру)
```

Здесь **Domain ни от кого не зависит**. Он в центре:
- Интерфейс `IOrderRepository` лежит в **Domain**
- Infrastructure **реализует** этот интерфейс (принцип DIP)

**Результат:** Domain чистый. Можно тестировать без БД, подставив фейковый репозиторий.

### Простая аналогия

```
❌ КЛАССИЧЕСКАЯ: Domain спрашивает у Infrastructure
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│   ┌────────┐                              ┌────────────────┐     │
│   │ Domain │ ──── "Как сохранить?" ────►  │ Infrastructure │     │
│   │        │                              │   (Database)   │     │
│   └────────┘                              └────────────────┘     │
│                                                                  │
│   Domain ЗАВИСИТ от Infrastructure (плохо для тестов)            │
└──────────────────────────────────────────────────────────────────┘


✅ СОВРЕМЕННАЯ: Infrastructure реализует интерфейс Domain
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│   ┌────────────────────────┐          ┌────────────────────┐     │
│   │        Domain          │          │   Infrastructure   │     │
│   │                        │          │                    │     │
│   │  interface IRepository │ ◄─────── │  PostgresRepo      │     │
│   │  {                     │ реализует│  implements        │     │
│   │    save(order)         │          │  IRepository       │     │
│   │  }                     │          │                    │     │
│   └────────────────────────┘          └────────────────────┘     │
│                                                                  │
│   Domain НЕ ЗАВИСИТ ни от кого (легко тестировать!)              │
└──────────────────────────────────────────────────────────────────┘
```

### Какую выбрать?

- **Классическая** — проще для старта, подходит для небольших проектов
- **Современная** — чище, лучше тестируется, подходит для больших проектов

**Обе версии используются.** Это не "старая vs новая", а "простая vs продвинутая".

## 📝 Пример потока "Создание заказа"

```
┌──────────────────────────────────────────────────────────────────────────┐
│  👤 Пользователь нажимает "Оформить заказ"                               │
└──────────────────────┬───────────────────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  PRESENTATION        │  OrderController.createOrder(JSON)                │
│                      │  Принимает данные, валидирует формат              │
└──────────────────────┼───────────────────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  APPLICATION         │  CreateOrderUseCase.execute(dto)                  │
│                      │  Координирует: "Проверь товар → Создай заказ →    │
│                      │  Сохрани → Отправь письмо"                        │
└──────────────────────┼───────────────────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  DOMAIN              │  Order.create(items, customer)                    │
│                      │  Проверяет: "Сумма >= 500? Товары в наличии?"     │
│                      │  Считает скидку, создаёт объект Order             │
└──────────────────────┼───────────────────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  INFRASTRUCTURE      │  PostgresOrderRepository.save(order)              │
│                      │  INSERT INTO orders... + EmailService.send()      │
└──────────────────────┴───────────────────────────────────────────────────┘
```

1. **UI**: Пользователь нажимает "Оформить". Контроллер принимает JSON.
2. **Application**: `CreateOrderUseCase` получает данные.
3. **Domain**: Создается объект `Order`. Проверяется, что товаров достаточно. Рассчитывается скидка.
4. **Infrastructure**: Репозиторий сохраняет `Order` в таблицу SQL. Отправляется email.

## ✅ Плюсы и ❌ Минусы

**Плюсы:**
- **Разделение ответственности:** Легко понять, куда положить новый код.
- **Тестируемость:** Можно тестировать Домен изолированно от Базы Данных.
- **Заменяемость:** Можно сменить базу данных (Инфраструктуру), не трогая Домен.

**Минусы:**
- **Boilerplate:** Много слоев, классов-оберток, DTO (Data Transfer Objects).
- **Протекание логики:** Иногда бывает лень создавать слой и пишут логику в контроллере (Anti-pattern).

## 🖼 Визуальная схема

```
┌─────────────────────────────────────────┐
│         PRESENTATION (UI)               │  ← Контроллеры, API endpoints
│         Кнопки, формы, JSON             │
├─────────────────────────────────────────┤
│         APPLICATION                     │  ← Use Cases, сервисы-координаторы
│         "Что делать?"                   │
├─────────────────────────────────────────┤
│         DOMAIN                          │  ← Сущности, бизнес-правила
│         "Как работает бизнес?"          │     ❤️ СЕРДЦЕ
├─────────────────────────────────────────┤
│         INFRASTRUCTURE                  │  ← БД, Email, внешние API
│         "Как технически реализовать?"   │
└─────────────────────────────────────────┘

        Зависимости идут СВЕРХУ ВНИЗ ↓
```

## 📁 Пример структуры папок (Node.js / Python)

```
src/
├── presentation/          # Слой UI
│   ├── controllers/
│   │   └── OrderController.ts
│   └── routes/
│       └── orderRoutes.ts
│
├── application/           # Слой приложения
│   ├── use-cases/
│   │   └── CreateOrderUseCase.ts
│   └── dto/
│       └── CreateOrderDTO.ts
│
├── domain/                # Доменный слой (СЕРДЦЕ)
│   ├── entities/
│   │   └── Order.ts
│   ├── value-objects/
│   │   └── Money.ts
│   └── repositories/
│       └── IOrderRepository.ts   # ← Интерфейс (не реализация!)
│
└── infrastructure/        # Слой инфраструктуры
    ├── persistence/
    │   └── PostgresOrderRepository.ts  # ← Реализация интерфейса
    └── external/
        └── StripePaymentService.ts
```

**Обрати внимание:** В `domain/repositories/` лежит только **интерфейс** `IOrderRepository`. А **реализация** (`PostgresOrderRepository`) — в `infrastructure/`. Это DIP в действии!

## ⚠️ Частые ошибки Junior-ов

### Ошибка 1: Бизнес-логика в контроллере

```python
# ❌ ПЛОХО — логика в контроллере
@app.route('/orders', methods=['POST'])
def create_order():
    data = request.json
    
    # Бизнес-логика здесь — НЕПРАВИЛЬНО!
    if data['total'] < 500:
        return {"error": "Минимальная сумма 500 руб"}, 400
    
    order = Order(data)
    db.session.add(order)
    db.session.commit()
    return {"id": order.id}
```

```python
# ✅ ХОРОШО — логика в Domain
# domain/entities/order.py
class Order:
    def __init__(self, total):
        if total < 500:
            raise ValueError("Минимальная сумма 500 руб")
        self.total = total

# presentation/controllers/order_controller.py
@app.route('/orders', methods=['POST'])
def create_order():
    data = request.json
    order = create_order_use_case.execute(data)  # Делегируем Application слою
    return {"id": order.id}
```

### Ошибка 2: Domain зависит от базы данных

```python
# ❌ ПЛОХО — Domain импортирует SQLAlchemy
from sqlalchemy import Column, Integer  # НЕТ!

class Order:
    id = Column(Integer)  # Domain знает про БД — плохо!
```

```python
# ✅ ХОРОШО — Domain чистый, Infrastructure знает про БД
# domain/entities/order.py
class Order:
    def __init__(self, id, total):
        self.id = id
        self.total = total

# infrastructure/persistence/order_model.py
from sqlalchemy import Column, Integer
class OrderModel(Base):  # Это модель БД, не Domain!
    id = Column(Integer)
```

### Ошибка 3: Пропуск Application слоя

Часто Junior-ы пишут: `Controller → Repository` напрямую.

```
❌ НЕПРАВИЛЬНО (пропущен Application):

┌────────────┐      ┌────────────┐      ┌────────────┐
│ Controller │ ───► │   Domain   │ ───► │ Repository │
└────────────┘      └────────────┘      └────────────┘
      │                                        │
      └────────────────────────────────────────┘
                  Напрямую! Плохо!


✅ ПРАВИЛЬНО (через Application):

┌────────────┐      ┌─────────────┐      ┌────────────┐      ┌────────────┐
│ Controller │ ───► │ Application │ ───► │   Domain   │ ───► │ Repository │
└────────────┘      │  (UseCase)  │      └────────────┘      └────────────┘
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │EmailService │  ← Легко добавить!
                    └─────────────┘
```

```python
# ❌ Контроллер напрямую работает с репозиторием
def create_order():
    order = Order(request.json)
    order_repo.save(order)  # Пропустили Application слой!
```

**Почему плохо?** Если завтра после создания заказа нужно отправить email — придётся менять контроллер. А если заказы создаются из 3 разных мест?

## 🔗 Связь с другими архитектурами

Layered Architecture — это **базовый** паттерн. На его основе построены более продвинутые:

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           LAYERED (классика)                                    │
│                                                                                 │
│    ┌──────────────────┐     Слои идут СВЕРХУ ВНИЗ                               │
│    │        UI        │     UI → App → Domain → Infra                           │
│    ├──────────────────┤                                                         │
│    │   Application    │     Самая простая для понимания.                        │
│    ├──────────────────┤     Подходит для старта.                                │
│    │      Domain      │                                                         │
│    ├──────────────────┤                                                         │
│    │  Infrastructure  │                                                         │
│    └──────────────────┘                                                         │
│            ↓                                                                    │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│                         CLEAN / ONION Architecture                              │
│                                                                                 │
│    ┌─────────────────────────────────┐     Зависимости идут К ЦЕНТРУ            │
│    │         Infrastructure          │                                          │
│    │    ┌───────────────────────┐    │     Domain в ЦЕНТРЕ, ни от кого          │
│    │    │      Application      │    │     не зависит.                          │
│    │    │    ┌─────────────┐    │    │                                          │
│    │    │    │   DOMAIN    │    │    │     Как луковица: внешние слои           │
│    │    │    │   ❤️ ЯДРО   │    │    │     зависят от внутренних.               │
│    │    │    └─────────────┘    │    │                                          │
│    │    └───────────────────────┘    │                                          │
│    └─────────────────────────────────┘                                          │
│                    ↑                                                            │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│                      HEXAGONAL (Ports & Adapters)                               │
│                                                                                 │
│       Adapter                                    Adapter                        │
│    (REST API) ◄────┐                      ┌────► (Database)                     │
│                    │                      │                                     │
│       Adapter      │  ┌──────────────┐    │      Adapter                        │
│     (CLI) ◄────────┼──│   APP CORE   │────┼────► (Email SMTP)                   │
│                    │  │              │    │                                     │
│       Adapter      │  │ Domain +     │    │      Adapter                        │
│    (gRPC) ◄────────┘  │ Application  │    └────► (Redis Cache)                  │
│                       └──────────────┘                                          │
│                                                                                 │
│    Приложение в центре. "Порты" — интерфейсы. "Адаптеры" — реализации.          │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**Совет:** Начни с Layered, потом изучи Clean Architecture — это следующий уровень.

## 📋 Чек-лист: Когда использовать Layered Architecture?

- [ ] Проект больше 3-5 файлов и будет расти?
- [ ] Нужно разделить бизнес-логику от UI и базы данных?
- [ ] В команде больше 1 человека?
- [ ] Планируешь писать тесты?
- [ ] Возможна смена технологий (БД, фреймворк)?

**Если "да" хотя бы на 2 пункта → используй Layered Architecture.**

**Если проект маленький** (скрипт, простой CRUD без сложной логики) — можно обойтись без слоёв.

---

## 🎓 Главное для Junior:

1. **4 слоя:** UI → Application → Domain → Infrastructure.
2. **Domain — сердце.** В современной архитектуре он не знает про БД (DIP), в классической — зависит от Infrastructure.
3. **Зависимости сверху вниз** (или к центру в Clean Architecture).
4. **Не пиши бизнес-логику в контроллерах** — это главная ошибка.
5. **Интерфейсы в Domain, реализации в Infrastructure** — это DIP.

**Запомни:** Если кто-то спросит "куда положить этот код?" — ответ зависит от того, *что* этот код делает:
- Принимает HTTP? → **Presentation**
- Координирует действия? → **Application**
- Проверяет бизнес-правила? → **Domain**
- Работает с БД/API? → **Infrastructure**
