# Шпаргалка: как выбирать паттерны (быстро и по делу)

Этот файл нужен, чтобы **научиться думать паттернами** — не зубрить названия, а видеть ситуации, где они помогают.

**Главное правило:**
- Сначала проблема → потом паттерн (не наоборот!)
- Если задача решается простым кодом — **не усложняй**

---

## 🧠 Как думать при проектировании (ДО написания кода)

Перед тем как писать код, задай себе эти вопросы:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ ПЕРЕД КОДОМ                                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. ЧТО МЕНЯЕТСЯ?                                                           │
│     - Какие части системы будут меняться чаще всего?                        │
│     - Что может добавиться завтра? (новый способ оплаты? новый тип юзера?)  │
│     → То, что меняется — выноси отдельно (Strategy, Factory)                │
│                                                                             │
│  2. КТО С КЕМ ОБЩАЕТСЯ?                                                     │
│     - Кто вызывает кого?                                                    │
│     - Есть ли "одно событие → много реакций"?                               │
│     → Если да — Observer                                                    │
│                                                                             │
│  3. ГДЕ ГРАНИЦЫ?                                                            │
│     - Где кончается "мой код" и начинается "внешний мир" (БД, API, UI)?     │
│     - Что если завтра сменится БД / фреймворк / внешний сервис?             │
│     → Границы = Порты и Адаптеры (Hexagonal) или слои (Layered)             │
│                                                                             │
│  4. ГДЕ ЖИВУТ ПРАВИЛА БИЗНЕСА?                                              │
│     - "Заказ не может быть меньше 500 руб" — это где?                       │
│     - В контроллере? В базе? В JS на фронте?                                │
│     → Правила должны жить в Domain (не размазывай!)                         │
│                                                                             │
│  5. КАК Я БУДУ ЭТО ТЕСТИРОВАТЬ?                                             │
│     - Могу ли я протестировать логику БЕЗ базы данных и HTTP?               │
│     - Если нет — значит, зависимости перепутаны                             │
│     → Инверсия зависимостей (порты/интерфейсы)                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 🚨 Красные флаги (код кричит о рефакторинге)

Когда видишь это в коде — **остановись и подумай о паттерне**:

```
┌──────────────────────────────────────┬──────────────────────────────────────┐
│  🚨 СИМПТОМ                          │  💡 ЧТО ПОМОЖЕТ                      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  if type == "A": ... elif "B" ...    │  Strategy или Factory                │
│  (и таких условий 5+)                │                                      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  После X нужно сделать Y, Z, W...    │  Observer                            │
│  (и список действий растёт)          │                                      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  Копипаста создания объектов         │  Factory                             │
│  в разных местах                     │                                      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  Внешний API возвращает "не то"      │  Adapter                             │
│  и ты конвертируешь везде            │                                      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  Хочешь добавить логирование/кэш     │  Decorator                           │
│  ко многим классам                   │                                      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  Бизнес-логика в контроллере/роуте   │  Layered (вынести в Domain)          │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  Тесты требуют поднять всю БД        │  Hexagonal (порты + фейки)           │
├──────────────────────────────────────┼──────────────────────────────────────┤
│  Всё в одном файле, страшно трогать  │  MVC или Layered                     │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

## 🔗 Как паттерны работают ВМЕСТЕ (комбинации)

Паттерны редко живут по одному. Вот типичные связки:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  HEXAGONAL + FACTORY + OBSERVER                                             │
│  (Типичный backend-сервис)                                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐                 │
│   │  REST API   │      │   UseCase   │      │  Observer   │                 │
│   │  (Adapter)  │─────►│   (Core)    │─────►│  (события)  │                 │
│   └─────────────┘      └──────┬──────┘      └──────┬──────┘                 │
│                               │                    │                        │
│                               ▼                    ▼                        │
│                        ┌─────────────┐      ┌─────────────┐                 │
│                        │   Factory   │      │ Email, Log, │                 │
│                        │ (создание)  │      │  Analytics  │                 │
│                        └─────────────┘      └─────────────┘                 │
│                                                                             │
│   Пример: Создание заказа                                                   │
│   1. REST Adapter принимает запрос                                          │
│   2. UseCase вызывает Factory для создания нужного типа заказа              │
│   3. После создания — Observer уведомляет подписчиков (email, лог)          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  LAYERED + STRATEGY + ADAPTER                                               │
│  (Интернет-магазин с разной доставкой и платежами)                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Presentation:  OrderController                                            │
│        │                                                                    │
│        ▼                                                                    │
│   Application:   OrderService                                               │
│        │              │                                                     │
│        ▼              ▼                                                     │
│   Domain:        ┌─────────────┐     ┌─────────────┐                        │
│                  │  Strategy   │     │  Strategy   │                        │
│                  │ (доставка)  │     │  (оплата)   │                        │
│                  │             │     │             │                        │
│                  │ - Курьер    │     │ - Карта     │                        │
│                  │ - Почта     │     │ - PayPal    │                        │
│                  │ - Самовывоз │     │ - Крипта    │                        │
│                  └─────────────┘     └─────────────┘                        │
│        │                                                                    │
│        ▼                                                                    │
│   Infrastructure:  ┌─────────────┐                                          │
│                    │   Adapter   │  (Stripe API, Почта России API)          │
│                    └─────────────┘                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Как пользоваться этой шпаргалкой (30 секунд)

1. Посмотри, *где* проблема:
   - **В устройстве проекта целиком** (папки, слои) → см. «Архитектура»
   - **Внутри одной фичи** (if/else, создание объектов) → см. «Паттерны в коде»
2. Найди похожий симптом в таблице "Красные флаги"
3. Проверь «Когда НЕ использовать» в карточке паттерна
4. Если надо глубже — открой подробный конспект (ссылки в каждом блоке)

## Быстрый выбор по симптомам

### Архитектура (как устроить проект)

- **Проект растёт, код превращается в кашу** → `Layered Architecture`
  - Симптомы: контроллеры знают про SQL, бизнес-правила в API, трудно тестировать.
- **Хочешь "ядро" отдельно, а БД/API менять без боли** → `Hexagonal Architecture`
  - Симптомы: много интеграций, несколько входов (REST + CLI), хочется быстрых тестов без базы.
- **Нужен понятный разнос UI/логики/данных** → `MVC`
  - Симптомы: всё в одном файле, сложно менять UI, ломается логика.

### Паттерны в коде (как починить конкретный участок)

- **Много `if/elif` для разных вариантов** → `Strategy`
  - Примеры: разные способы доставки/оплаты/сортировки.
- **После события нужно сделать 3-5 действий** → `Observer`
  - Примеры: регистрация → email + лог + аналитика.
- **Создание объектов размазано и повторяется** → `Factory`
  - Примеры: "по типу создаём нужный клиент/платёж/заказ".
- **Нужно подружить твой код с чужим API** → `Adapter`
  - Пример: внешний сервис даёт Фаренгейты, а тебе нужны Цельсии.
- **Нужно добавить логирование/кэш поверх без изменения класса** → `Decorator`
  - Пример: обернуть отправку уведомлений логированием.

## Карточки паттернов (коротко)

### Layered Architecture (UI / Application / Domain / Infrastructure)

- **Бери, если**:
  - проект > 3-5 файлов и будет расти
  - хочешь, чтобы было понятно "куда класть код"
  - бизнес-логика должна жить отдельно от HTTP и БД
- **Не бери, если**:
  - маленький скрипт/одноразовая утилита
  - CRUD без сложных правил
- **Самый частый фейл**: бизнес-логика в контроллере, Domain зависит от БД.
- **Конспект**: `Layered_Architecture.md`

---

### Hexagonal Architecture (Ports & Adapters)

Простыми словами: **ядро приложения не знает про внешние штуки** (HTTP, БД, email). Оно знает только "мне нужен кто-то, кто умеет сохранить заказ" — это интерфейс (порт). А БД/HTTP — это адаптеры.

- **Бери, если**:
  - бизнес-логика важная и её нужно тестировать отдельно
  - много внешних зависимостей (БД, платежи, кэш)
  - несколько способов входа (REST, CLI, очереди)
  - хочешь легко менять Postgres → Mongo без переписывания ядра
- **Не бери, если**:
  - простой CRUD, где "сохранить/прочитать" — вся логика
  - команда маленькая и проект небольшой
- **Самый частый фейл**: ядро импортирует адаптеры (`from adapters...` в core).
- **Конспект**: `Hexagonal_Architecture.md`

---

### MVC

Простыми словами: разделяем на:
- **Model**: данные + логика
- **View**: то, что показываем (HTML/JSON)
- **Controller**: связывает Model и View

- **Бери, если**:
  - делаешь UI/веб
  - хочешь, чтобы UI можно было менять, не трогая логику
- **Не бери, если**:
  - это библиотека/backend без "View"
- **Самый частый фейл**: "всё в Controller".
- **Конспект**: `MVC.md`

---

### Strategy

Простыми словами: **одна задача — много способов сделать её**. Способы выносим отдельно и выбираем нужный.

- **Бери, если**:
  - 3+ вариантов поведения
  - варианты добавляются со временем
  - у тебя "ад из if/else"
- **Не бери, если**:
  - 1-2 варианта и больше не будет
  - логика совсем короткая
- **Самый частый фейл**: делать стратегии ради красоты, когда можно одной функцией.
- **Конспект**: `strategy pattern.md`

---

### Observer

Простыми словами: есть **событие**, и много "подписчиков", которые реагируют.

- **Бери, если**:
  - одно событие запускает много действий
  - подписчики могут добавляться/убираться
  - хочешь слабую связанность
- **Не бери, если**:
  - всего одно действие и оно всегда одно
  - порядок выполнения критичен и сложный
- **Самый частый фейл**: превращать систему в "магические события", где непонятно, кто что вызывает.
- **Конспект**: `observer_pattern.md`

---

### Factory / Factory Method

Простыми словами: **создание объектов прячем в одно место**, чтобы не размазывать `if/elif` по проекту.

- **Бери, если**:
  - создаёшь объекты разных типов по параметру
  - логика создания повторяется в нескольких местах
  - типы будут добавляться
- **Не бери, если**:
  - создаётся один и тот же класс без вариантов
  - создание только в одном месте
- **Самый частый фейл**: делать "фабрику ради фабрики".
- **Конспект**: `factory_method.md`

---

### Adapter

Простыми словами: **переводчик** между твоим интерфейсом и чужим.

- **Бери, если**:
  - нужно подключить внешний API/библиотеку с неудобным интерфейсом
  - есть "несовместимость форматов"
- **Не бери, если**:
  - ты контролируешь оба куска кода
- **Самый частый фейл**: делать один гигантский адаптер вместо маленьких.
- **Конспект**: `Adapter_Decorator_Notes.md`

---

### Decorator

Простыми словами: **обёртка**, которая добавляет поведение "поверх", не меняя код объекта.

- **Бери, если**:
  - нужно добавить логирование/кэш/проверки к нескольким классам
  - нужно комбинировать улучшения (логирование + сжатие + права)
- **Не бери, если**:
  - улучшение нужно в одном месте один раз
- **Самый частый фейл**: слишком много обёрток — трудно дебажить.
- **Конспект**: `Adapter_Decorator_Notes.md`

## 🏋️ Как тренироваться (практика)

### Упражнение 1: Анализ своего кода
1. Открой любой свой старый проект
2. Пройдись по таблице "Красные флаги"
3. Запиши: какие симптомы нашёл? Какой паттерн помог бы?

### Упражнение 2: Проектирование на бумаге
Перед написанием кода:
1. Нарисуй квадратики (компоненты)
2. Нарисуй стрелочки (кто кого вызывает)
3. Задай себе 5 вопросов из секции "Как думать при проектировании"
4. Отметь: где будут Strategy? Factory? Observer?

### Упражнение 3: Code Review с паттернами
Когда смотришь чужой код (или свой старый):
- Видишь длинный if/elif? → Strategy?
- Видишь "после X делаем Y, Z, W"? → Observer?
- Видишь создание объектов в 3 местах? → Factory?

```
│                                                                             │

│                                                                             │
│   2. Сначала напиши ПРОСТО. Паттерн добавь, когда появится БОЛЬ             │

│                                                                             │
│   4. Лучший код — тот, который ЛЕГКО МЕНЯТЬ и ЛЕГКО ТЕСТИРОВАТЬ             │
│                                                                             │
│   5. Учись видеть СИМПТОМЫ, а не запоминать названия паттернов              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```
