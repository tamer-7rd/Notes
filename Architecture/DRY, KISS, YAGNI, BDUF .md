# DRY, KISS, YAGNI, BDUF — для Junior

Эти 4 принципа — фундамент хорошего кода. Они проще, чем SOLID, но не менее важны.

---

## 1. 🌵 DRY (Don’t Repeat Yourself) — Не повторяйся

### 🎯 Суть
Каждый кусок знаний (логики) должен быть в единственном экземпляре.
Если ты скопировал код (`Ctrl+C`, `Ctrl+V`) — ты уже нарушил DRY.

### ❌ Плохо (Дублирование)
Логика подсчета налога повторяется в двух местах. Если налог изменится, придётся править везде (и можно забыть!).

```javascript
function calculatePhonePrice(price) {
  return price + (price * 0.2); // Налог 20%
}

function calculateLaptopPrice(price) {
  return price + (price * 0.2); // То же самое!
}
```

### ✅ Хорошо (Переиспользование)
Выносим общую логику в отдельную функцию.

```javascript
function addTax(price) {
  return price + (price * 0.2);
}

function calculatePhonePrice(price) {
  return addTax(price);
}

function calculateLaptopPrice(price) {
  return addTax(price);
}
```

**⚠️ Важно:** Не доводи до абсурда. Если код *выглядит* похоже, но делает *разные* по смыслу вещи — не объединяй их.

## 2. 💋 KISS (Keep It Simple, Stupid) — Будь проще

### 🎯 Суть
Самое простое решение — обычно самое лучшее. Не пиши сложный код, если можно написать простой.
Код должен быть понятен даже стажеру, который видит его первый раз.

### ❌ Плохо (Переусложнение)
Ты решил выпендриться знанием однострочников и методов массивов.

```javascript
// Что здесь происходит?! 🤯
const getInitials = name => name.split(' ').map((n, i) => i === 0 || i === name.split(' ').length - 1 ? n[0].toUpperCase() : '').join('');
```

### ✅ Хорошо (Читаемость)
Пишем так, чтобы было понятно.

```javascript
function getInitials(fullName) {
  const parts = fullName.split(' ');
  const first = parts[0][0].toUpperCase();
  const last = parts[parts.length - 1][0].toUpperCase();
  return first + last;
}
```

**Правило:** Код пишется один раз, а читается — сотни раз. Пиши для людей.

## 3. 🛑 YAGNI (You Aren’t Gonna Need It) — Тебе это не понадобится

### 🎯 Суть
Не пиши код "на будущее". Реализуй только то, что нужно **прямо сейчас**.
"А вдруг нам потом понадобится поддержка Марсианских тугриков?" — Вот когда понадобится, тогда и напишешь.

### ❌ Плохо (Гадание на кофейной гуще)
Задача: "Сделать кнопку 'Купить'".
Ты пишешь:
*   Кнопку "Купить".
*   Кнопку "В избранное" (вдруг захотят?).
*   Систему скидок (на будущее).
*   Экспорт чека в PDF (ну круто же!).

**Итог:** Потратил неделю, а заказчику нужна была только кнопка. Остальной код мешает и в нём могут быть баги.

### ✅ Хорошо (Фокус на задаче)
Задача: "Сделать кнопку 'Купить'".
Ты пишешь:
*   Кнопку "Купить".

**Итог:** Сделал за час, код чистый, багов нет.

## 4. 🏗️ BDUF (Big Design Up Front) — Большое проектирование заранее

### 🎯 Суть
Подход, когда перед написанием кода ты **полностью** проектируешь систему до мелочей.
*Противоположность Agile.*

### ⚖️ Плюсы и минусы

```
+----------------------------------+--------------------------------------------------+
| Плюсы                            | Минусы                                           |
+----------------------------------+--------------------------------------------------+
| Чёткий план, меньше хаоса.       | Требования могут измениться, а план уже утверждён|
+----------------------------------+--------------------------------------------------+
| Понятные сроки и бюджет.         | "Паралич анализа" — можно проектировать вечно    |
|                                  | и не начать кодить.                              |
+----------------------------------+--------------------------------------------------+
```

### 🎓 Для Junior:
В современном мире (Agile/Scrum) чистый BDUF используется редко.
Обычно используется **"Достаточное проектирование"**:
1. Набросай схему БД.
2. Опиши API.
3. Начни кодить.
4. Корректируй по ходу.

Не пытайся предусмотреть всё на старте — это невозможно.

## 📋 Чек-лист для твоего кода (Pull Request)

Перед тем как отправить код на проверку, пройдись по пунктам:

1.  [ ] **DRY:** Нет ли у меня копипасты? Можно ли вынести в общую функцию?
2.  [ ] **KISS:** Понятен ли мой код? Можно ли написать проще? Не слишком ли я "закрутил"?
3.  [ ] **YAGNI:** Не написал ли я лишних функций "про запас"?

Если везде "ОК" — ты молодец! 🚀
