# Как проектировать систему ДО написания кода

Этот конспект — пошаговый гайд для junior-а: как думать о системе **до** того, как откроешь редактор кода.

**Главная идея:** Архитектуру меняем до кода — дёшево. После кода — дорого и больно.

---

## 📋 Чек-лист: Что решить ДО кода

Перед тем как писать код, ответь на эти вопросы. Не нужно писать документ на 50 страниц — достаточно заметок на листочке или в голове.

### 1. Что делает система? (Scope)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ:                                                                   │
│                                                                             │
│  • Какую проблему решаем?                                                   │
│  • Кто пользователь? (человек, другая система, оба)                         │
│  • Что система НЕ делает? (границы)                                         │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  ПРИМЕР:                                                                    │
│                                                                             │
│  "Сервис заказов для интернет-магазина"                                     │
│  - Создание заказа, отмена, просмотр статуса                                │
│  - Пользователи: покупатели (через сайт), админы (через панель)             │
│  - НЕ делает: оплату (это отдельный сервис), доставку (тоже отдельно)       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2. Какие данные и как хранятся? (Data)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ:                                                                   │
│                                                                             │
│  • Какие основные сущности? (User, Order, Product...)                       │
│  • Как они связаны? (Order содержит Products, User создаёт Orders)          │
│  • Где хранить? (PostgreSQL, MongoDB, Redis, файлы)                         │
│  • Сколько данных? (100 записей или 100 миллионов)                          │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  ПРИМЕР:                                                                    │
│                                                                             │
│   ┌─────────┐       ┌─────────┐       ┌─────────┐                           │
│   │  User   │──────►│  Order  │◄──────│ Product │                           │
│   └─────────┘  1:N  └─────────┘  N:M  └─────────┘                           │
│                                                                             │
│   - User: id, email, name                                                   │
│   - Order: id, user_id, status, total, created_at                           │
│   - Product: id, name, price                                                │
│   - OrderItem: order_id, product_id, quantity                               │
│                                                                             │
│   Хранение: PostgreSQL (нужны транзакции, связи)                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3. Кто и как взаимодействует с системой? (Interfaces)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ:                                                                   │
│                                                                             │
│  • Какие точки входа? (REST API, GraphQL, CLI, очереди, cron)               │
│  • Кто вызывает систему? (фронтенд, другой сервис, админ)                   │
│  • С какими внешними системами общаемся? (платежи, email, другие API)       │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  ПРИМЕР:                                                                    │
│                                                                             │
│                    ┌─────────────────────┐                                  │
│   Фронтенд ───────►│                     │───────► PostgreSQL               │
│   (REST API)       │                     │                                  │
│                    │   ORDER SERVICE     │───────► Payment API (Stripe)     │
│   Админка ────────►│                     │                                  │
│   (REST API)       │                     │───────► Email Service            │
│                    └─────────────────────┘                                  │
│                              ▲                                              │
│                              │                                              │
│   Inventory Service ─────────┘ (проверка наличия)                           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 4. Где какой код живёт? (Structure)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ:                                                                   │
│                                                                             │
│  • Какую архитектуру использовать? (Layered, Hexagonal, MVC)                │
│  • Как разбить на папки/модули?                                             │
│  • Где будет бизнес-логика? (Domain слой)                                   │
│  • Где будет работа с БД? (Infrastructure слой)                             │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  ПРИМЕР (Layered):                                                          │
│                                                                             │
│   src/                                                                      │
│   ├── presentation/      ← REST контроллеры                                 │
│   │   └── OrderController                                                   │
│   ├── application/       ← Use Cases (координация)                          │
│   │   └── CreateOrderUseCase                                                │
│   ├── domain/            ← Бизнес-логика (СЕРДЦЕ)                           │
│   │   ├── Order (сущность)                                                  │
│   │   └── OrderRepository (интерфейс!)                                      │
│   └── infrastructure/    ← Работа с внешним миром                           │
│       ├── PostgresOrderRepository                                           │
│       └── StripePaymentService                                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Как выбрать архитектуру:**

| Ситуация | Архитектура |
|----------|-------------|
| Простой проект, 1-2 разработчика | MVC или простой Layered |
| Средний проект, важна бизнес-логика | Layered (4 слоя) |
| Сложный проект, много интеграций, нужны тесты | Hexagonal |

### 5. Что может пойти не так? (Risks)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ:                                                                   │
│                                                                             │
│  • Что если БД упадёт?                                                      │
│  • Что если внешний сервис (Stripe) не отвечает?                            │
│  • Что если придёт 1000 запросов в секунду?                                 │
│  • Какие данные нельзя потерять?                                            │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  ПРИМЕР:                                                                    │
│                                                                             │
│  Риск: Stripe не отвечает                                                   │
│  Решение: Retry с экспоненциальной задержкой + статус "payment_pending"     │
│                                                                             │
│  Риск: Дублирование заказов (пользователь нажал 2 раза)                     │
│  Решение: Idempotency key (уникальный ключ запроса)                         │
│                                                                             │
│  Риск: Потеря заказа                                                        │
│  Решение: Сначала сохраняем в БД, потом отправляем в Stripe                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 6. Как буду это тестировать? (Testing)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  ВОПРОСЫ:                                                                   │
│                                                                             │
│  • Могу ли я протестировать бизнес-логику БЕЗ базы данных?                  │
│  • Как замокать внешние сервисы (Stripe, Email)?                            │
│  • Какие сценарии критичны и должны быть покрыты тестами?                   │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  ПРИМЕР:                                                                    │
│                                                                             │
│  Unit тесты (быстрые, без БД):                                              │
│  - Order.create() с невалидными данными → ошибка                            │
│  - Order.cancel() когда статус "delivered" → ошибка                         │
│                                                                             │
│  Integration тесты (с БД):                                                  │
│  - Создать заказ → проверить, что сохранился                                │
│  - Отменить заказ → проверить, что статус изменился                         │
│                                                                             │
│  Как это влияет на архитектуру:                                             │
│  → Нужны интерфейсы (порты), чтобы подставлять фейки в тестах               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 🛠 Пошаговый процесс проектирования

### Шаг 1: Пойми задачу (10 мин)

- Прочитай требования / поговори с заказчиком
- Запиши: что система ДЕЛАЕТ и что НЕ ДЕЛАЕТ
- Выпиши основные сущности (User, Order, Product...)

### Шаг 2: Нарисуй "квадратики и стрелочки" (15 мин)

Не нужен UML или специальные инструменты. Листок бумаги или draw.io.

```
Пример "квадратиков":

┌──────────┐         ┌──────────────┐         ┌──────────┐
│ Frontend │ ──────► │ Order Service│ ──────► │ Database │
└──────────┘         └──────┬───────┘         └──────────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ Stripe API   │
                    └──────────────┘
```

### Шаг 3: Определи слои/структуру (10 мин)

- Выбери архитектуру (Layered / Hexagonal / MVC)
- Набросай структуру папок
- Реши, где будет бизнес-логика

### Шаг 4: Продумай "что если" (10 мин)

- Что если внешний сервис не отвечает?
- Что если данных станет много?
- Что если появится новый тип пользователя/заказа?

### Шаг 5: Начни с малого (код)

- Не пытайся реализовать всё сразу
- Начни с одного use case (например, "создать заказ")
- Убедись, что структура работает, потом добавляй остальное

- Integration: что тестируем с БД

## ⚠️ Частые ошибки при проектировании

### Ошибка 1: Слишком много деталей сразу

```
❌ "Нарисую все 50 эндпоинтов и все поля всех таблиц"
   → Потратишь 3 дня, а потом требования изменятся

✅ "Нарисую основные компоненты и главный flow"
   → 30 минут, и можно начинать код
```

### Ошибка 2: Проектирование без понимания требований

```
❌ "Сделаю микросервисы, потому что это круто"
   → Для проекта с 2 пользователями это overkill

✅ "Сначала пойму, что нужно, потом выберу архитектуру"
   → Архитектура соответствует задаче
```

### Ошибка 3: Игнорирование "что если"

```
❌ "Stripe всегда работает, зачем думать об ошибках"
   → Через месяц: 500 ошибок в проде, пользователи злятся

✅ "Что если Stripe не отвечает? Сделаю retry и fallback"
   → Система устойчива к сбоям
```

### Ошибка 4: Не думать о тестировании

```
❌ "Тесты напишу потом"
   → Архитектура не позволяет тестировать без БД

✅ "Как я это протестирую?"
   → Сразу делаешь интерфейсы и инверсию зависимостей
```

## 🆚 Что решаем ЗАРАНЕЕ vs ПО ХОДУ

```
┌─────────────────────────────────────┬─────────────────────────────────────┐
│  РЕШАЕМ ЗАРАНЕЕ                     │  ДОБАВЛЯЕМ ПО ХОДУ                  │
│  (дорого менять потом)              │  (легко добавить позже)             │
├─────────────────────────────────────┼─────────────────────────────────────┤
│                                     │                                     │
│  • Общая архитектура                │  • Strategy (вместо if/else)        │
│    (Layered / Hexagonal)            │                                     │
│                                     │  • Factory (когда 3+ типа)          │
│  • Где живёт бизнес-логика          │                                     │
│    (Domain слой)                    │  • Observer (когда 3+ реакции)      │
│                                     │                                     │
│  • Как общаемся с внешним миром     │  • Decorator (когда нужен           │
│    (через интерфейсы/порты)         │    логирование/кэш везде)           │
│                                     │                                     │
│  • Структура папок                  │  • Конкретные оптимизации           │
│                                     │                                     │
│  • Основные сущности и связи        │  • Дополнительные поля/методы       │
│                                     │                                     │
└─────────────────────────────────────┴─────────────────────────────────────┘
```

## 🎓 Главное для Junior

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│  1. 30 МИНУТ ПРОЕКТИРОВАНИЯ экономят 30 ЧАСОВ переписывания                 │
│                                                                             │
│  2. Не нужен идеальный план — нужно НАПРАВЛЕНИЕ                             │

│                                                                             │

│                                                                             │

│                                                                             │
│  5. Начни с ПРОСТОЙ архитектуры. Усложнить всегда успеешь.                  │
│     Layered > Hexagonal для начала                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```
