# Очереди сообщений (Message Queues): RabbitMQ и Apache Kafka

Привет! 👋 Сегодня мы разберем очень важную тему в архитектуре backend-приложений — **Очереди сообщений (Message Queues)**.

Представь, что ты работаешь в кофейне бариста.
1.  **Синхронный подход (без очереди):** Клиент делает заказ, и ты *сразу же* начинаешь готовить кофе. Клиент ждет у кассы, пока ты не закончишь. Следующий клиент не может сделать заказ, пока ты занят. Если кофе готовится 5 минут, очередь на вход растет, клиенты злятся и уходят.
2.  **Асинхронный подход (с очередью):** Клиент делает заказ, кассир выбивает чек и клеит его на стойку (в очередь). Клиент уходит ждать за столик. Бариста (ты) берешь чек, когда освободишься, готовишь кофе и выкрикиваешь имя. Кассир может принимать заказы очень быстро, не дожидаясь, пока кофе будет готов.

Вот эта "стойка с чеками" и есть **Брокер сообщений (Message Broker)**.

---

## 1. Зачем это нужно в программировании?

В реальных приложениях (микросервисах или даже монолитах) нам часто нужно выполнять задачи, которые занимают время (отправка email, обработка видео, генерация отчетов) или просто передавать данные между сервисами.

Основные причины использовать очереди:

1.  **Асинхронность (Фоновые задачи):** Не заставлять пользователя ждать.
    *   *Пример:* Пользователь зарегистрировался. Нам нужно отправить ему приветственный Email. Отправка письма может занять 1-2 секунды. Зачем пользователю смотреть на крутящийся спиннер? Мы сохраняем пользователя в БД, кидаем задачу "Отправь Email" в очередь и сразу говорим пользователю "Успешно!". А специальный работник (Consumer) в фоне разберет очередь и отправит письмо.
2.  **Разделение ответственности (Decoupling):** Сервис А не должен знать, как работает Сервис Б.
    *   *Пример:* Сервис "Заказы" просто кидает событие `OrderCreated` (Заказ создан). Его могут слушать сервис "Склад" (чтобы зарезервировать товар), сервис "Логистика" (чтобы вызвать курьера) и сервис "Аналитика". Если мы добавим новый сервис, нам не нужно менять код сервиса "Заказы".
3.  **Сглаживание пиковых нагрузок (Traffic Smoothing / Throttling):**
    *   *Пример:* В черную пятницу пришло 10,000 заказов в секунду. Если мы будем обрабатывать их синхронно, база данных упадет. С очередью мы просто сложим все 10,000 заказов в буфер (очередь). А наши обработчики (Consumers) будут разгребать их с той скоростью, с которой могут (например, по 500 в секунду), не роняя систему.
4.  **Надежность:** Если сервис обработки упал, сообщения не пропадут. Они останутся лежать в очереди (брокере), пока сервис не поднимется и не обработает их.

## 2. Основные понятия

*   **Producer (Продюсер/Издатель):** Тот, кто создает сообщение и отправляет его в брокер (например, наш API сервер).
*   **Consumer (Консьюмер/Потребитель/Подписчик):** Тот, кто читает сообщения из брокера и выполняет работу (например, фоновый worker).
*   **Message Broker (Брокер):** Промежуточный сервис (программа), который принимает сообщения, хранит их и отдает потребителям. (Это и есть RabbitMQ или Kafka).
*   **Queue (Очередь):** Буфер внутри брокера, где хранятся сообщения.
*   **Message (Сообщение):** Данные, которые мы передаем (обычно JSON).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        Базовая схема Message Queue                          │
└─────────────────────────────────────────────────────────────────────────────┘

   ┌──────────────┐                                      ┌──────────────┐
   │   PRODUCER   │                                      │   CONSUMER   │
   │  (API, App)  │                                      │   (Worker)   │
   └──────┬───────┘                                      └──────▲───────┘
          │                                                     │
          │  publish()                                 get() / subscribe()
          │                                                     │
          ▼                                                     │
   ┌──────────────────────────────────────────────────────────────────────┐
   │                         MESSAGE BROKER                               │
   │  ┌────────────────────────────────────────────────────────────────┐  │
   │  │                         QUEUE                                  │  │
   │  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                      │  │
   │  │  │ msg │ │ msg │ │ msg │ │ msg │ │ msg │  ──────────────────▶ │  │
   │  │  └─────┘ └─────┘ └─────┘ └─────┘ └─────┘         FIFO         │  │
   │  └────────────────────────────────────────────────────────────────┘  │
   │                      (RabbitMQ / Kafka / Redis)                      │
   └──────────────────────────────────────────────────────────────────────┘
```

## 3. RabbitMQ vs Apache Kafka

Это два самых популярных инструмента, но они работают по-разному и подходят для разных задач.

### 🐰 RabbitMQ (Умный брокер, глупые потребители)

RabbitMQ — это классический брокер сообщений. Он работает как **почтовое отделение**.

*   **Как работает:**
    1.  Продюсер отправляет письмо.
    2.  RabbitMQ смотрит на адрес и кладет письмо в нужный ящик (Очередь).
    3.  Консьюмер забирает письмо.
    4.  **Важно:** Как только письмо доставлено и обработано, RabbitMQ **удаляет** его из очереди.
*   **Гарантии:** RabbitMQ очень старается доставить сообщение и убедиться, что оно обработано (Ack - подтверждение).
*   **Сложная маршрутизация:** Может отправлять сообщения разным получателям в зависимости от правил (Routing Keys).
*   **Когда использовать:**
    *   Для фоновых задач (отправка email, обработка картинок).
    *   Когда нужна гарантия доставки и сложная логика маршрутизации.
    *   Когда задачи долгие и их нужно распределять между работниками.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            🐰 RabbitMQ (Push)                               │
└─────────────────────────────────────────────────────────────────────────────┘

  Producer                                                      Consumers
     │                                                         ┌─────────┐
     │          ┌────────────────────────────────────────────▶│Worker 1 │
     │          │                                              └─────────┘
     │          │    ┌───────────────────────────────────┐     ┌─────────┐
     │   ┌──────┴──┐ │  QUEUE   [msg][msg][msg] ───────▶├────▶│Worker 2 │
     └──▶│EXCHANGE │─┤  (FIFO)  Сообщение УДАЛЯЕТСЯ     │     └─────────┘
         │ (router)│ │          после ack               │     ┌─────────┐
         └─────────┘ └───────────────────────────────────┘────▶│Worker 3 │
              │                                                └─────────┘
              │      Брокер сам ПРОТАЛКИВАЕТ (push) сообщения воркерам
              │      Round-robin: каждый воркер получает свои задачи
              ▼
         Routing по ключу / fanout / topic

```

### 🐘 Apache Kafka (Глупый брокер, умные потребители)

Kafka — это не просто очередь, это **распределенный журнал событий (Log)**. Представь себе бесконечную ленту логов, куда только дописываются новые записи.

*   **Как работает:**
    1.  Продюсер пишет событие в конец журнала (Topic).
    2.  Сообщение сохраняется на диск и **не удаляется** после прочтения (хранится заданное время, например, 7 дней).
    3.  Консьюмеры сами помнят, на каком месте (Offset) они остановились читать журнал. Они могут перечитать сообщения заново.
*   **Производительность:** Kafka создана для **огромных** объемов данных (миллионы сообщений в секунду).
*   **Когда использовать:**
    *   Сбор логов и метрик с тысяч серверов.
    *   Event Sourcing (сохранение истории изменений).
    *   Стриминг данных (аналитика в реальном времени, действия пользователей на сайте).
    *   Когда потребителей много и каждому нужна своя копия всех данных.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            🐘 Apache Kafka (Pull)                           │
└─────────────────────────────────────────────────────────────────────────────┘

  Producer           TOPIC: "orders"                          Consumer Groups
     │               (распределённый лог)
     │          ┌─────────────────────────────────────────────────────────┐
     │          │  Partition 0:  [msg0][msg1][msg2][msg3][msg4]...       │
     │          │                                    ▲                   │
     └─────────▶│  Partition 1:  [msg0][msg1][msg2]  │ offset=2          │
                │                                    │                   │
                │  Partition 2:  [msg0][msg1]        │                   │
                └────────────────────────────────────┼───────────────────┘
                                                     │
                    Сообщения НЕ удаляются!          │ poll()
                    Хранятся 7 дней (настраивается)  │
                                                     │
                          ┌──────────────────────────┴──────────────────┐
                          │                                             │
                    Consumer Group A                        Consumer Group B
                   ┌─────────────────┐                    ┌─────────────────┐
                   │ Consumer 1 (P0) │                    │ Consumer 1      │
                   │ Consumer 2 (P1) │                    │ (все партиции)  │
                   │ Consumer 3 (P2) │                    │                 │
                   └─────────────────┘                    └─────────────────┘
                   offset хранит сам                      Своя копия данных!
                   консьюмер (или Kafka)

```

## 4. Сравнение "на пальцах"

| Характеристика | RabbitMQ 🐰 | Kafka 🐘 |
| :--- | :--- | :--- |
| **Модель** | Очередь (Push). Брокер проталкивает сообщения консьюмеру. | Журнал (Pull). Консьюмер сам тянет сообщения. |
| **Удаление** | Сообщение удаляется после обработки. | Сообщение хранится долго (дни/недели). |
| **Повтор** | Сложно перечитать обработанное. | Легко "отмотать назад" и перечитать. |
| **Скорость** | Быстро (тысячи/сек). | Невероятно быстро (миллионы/сек). |
| **Сценарий** | "Сделай работу и забудь" (Job Queue). | "Запиши, что произошло" (Event Stream). |

## 5. Пример из жизни (Регистрация пользователя)

Давай посмотрим, как это выглядит в коде (псевдокод).

**Задача:** Пользователь регистрируется. Нужно:
1. Сохранить его в БД.
2. Отправить Email "Добро пожаловать".
3. Отправить данные в сервис Аналитики.

### Без очередей (Плохо ❌)
```python
def register_user(user_data):
    # 1. Сохраняем в БД (50ms)
    db.save(user_data)
    
    # 2. Шлем Email (SMTP медленный, 2000ms)
    # Если тут ошибка, пользователь увидит ошибку регистрации!
    email_service.send_welcome_email(user_data.email)
    
    # 3. Шлем в аналитику (HTTP запрос, 200ms)
    analytics_service.track_signup(user_data)
    
    return "Success" 
    # Итог: Пользователь ждет > 2 секунд. Риск сбоя высокий.
```

### С очередью RabbitMQ (Хорошо ✅)
```python
# API Сервер (Producer)
def register_user(user_data):
    # 1. Сохраняем в БД (50ms)
    user = db.save(user_data)
    
    # 2. Кидаем сообщение в очередь (очень быстро, 5ms)
    rabbitmq.publish(queue='email_queue', body={'user_id': user.id, 'email': user.email})
    rabbitmq.publish(queue='analytics_queue', body={'event': 'signup', 'user_id': user.id})
    
    return "Success" 
    # Итог: Пользователь ждет 55ms.
```

```python
# Email Worker (Consumer) - отдельный процесс
def listen_email_queue():
    while True:
        msg = rabbitmq.get_message('email_queue')
        if msg:
            try:
                # Тяжелая операция тут
                email_service.send_welcome_email(msg.email)
                rabbitmq.ack(msg) # Подтверждаем успех, сообщение удаляется
            except Exception:
                rabbitmq.nack(msg) # Ошибка, верни сообщение в очередь, попробуем позже!
```

## 6. Пример из реального проекта (Narraive): AI-обработка новости

Представим Narraive (агрегатор новостей + аналитика). Ты получил новую статью из внешнего API и хочешь:

1. Показать новость пользователю *сразу* (пусть даже без summary/tags).
2. В фоне прогнать текст через Python/LLM и получить `summary + tags`.
3. Сохранить результат в БД и обновить UI, когда обработка готова.
4. Если Python упал/LLM не ответил — сделать retry, не ломая продукт.

### Без очереди (Больно ❌)
```python
def ingest_article(article_payload):
    # 1. Сохраняем сырьё в БД
    article = db.articles.insert({
        'title': article_payload.title,
        'content': article_payload.content,
        'status': 'raw'
    })
    
    # 2. Синхронно идем в Python/LLM (может быть 5-30 секунд)
    ai = python_processor.summarize_and_tag(article.content)
    
    # 3. Обновляем БД
    db.articles.update(article.id, {
        'summary': ai.summary,
        'tags': ai.tags,
        'status': 'processed'
    })
    
    return "OK"
    # Итог: медленно, нестабильно, любой сбой ломает ingest.
```

### С очередью RabbitMQ (Нормально ✅)
```python
# BFF/API (Producer)
def ingest_article(article_payload):
    # 1. Сохраняем сырьё (быстро)
    article = db.articles.insert({
        'title': article_payload.title,
        'content': article_payload.content,
        'status': 'raw'
    })
    
    # 2. Кидаем задачу в очередь (быстро)
    rabbitmq.publish(
        queue='ai_process_queue',
        body={'article_id': article.id}
    )
    
    return "OK"
    # Итог: ingest быстрый, UI может сразу показать raw-новость.
```

```python
# AI Worker (Consumer) - отдельный процесс (часто на Python)
def listen_ai_process_queue():
    while True:
        msg = rabbitmq.get_message('ai_process_queue')
        if msg:
            try:
                article = db.articles.get(msg.article_id)
                
                # Идемпотентность: если уже обработано — просто подтверждаем и выходим
                if article.status == 'processed':
                    rabbitmq.ack(msg)
                    continue
                
                db.articles.update(article.id, {'status': 'processing'})
                
                ai = python_processor.summarize_and_tag(article.content)
                
                db.articles.update(article.id, {
                    'summary': ai.summary,
                    'tags': ai.tags,
                    'status': 'processed'
                })
                
                rabbitmq.ack(msg)
            except Exception:
                # Ошибка: верни сообщение в очередь, попробуем позже (retry)
                rabbitmq.nack(msg)
```

## 7. Level Up: Для Junior+/Middle (Production Ready) 🛠

Всё, что описано выше — база. В реальном продакшене (1+ год опыта) тебе нужно знать о **подводных камнях**.

### 7.1. RabbitMQ Exchanges (Маршрутизация)

В простом примере мы кидали сообщение сразу в очередь. Но в RabbitMQ между Producer и Queue стоит **Exchange (Обменник)**.

*   **Direct:** "Кинь сообщение точно в очередь `error_logs`". Строгое совпадение ключа.
*   **Fanout:** "Разошли это сообщение ВСЕМ очередям, которые ты знаешь". (Аналог паттерна Observer). Например, событие `UserRegistered` летит и в очередь Email, и в очередь Analytics одновременно.
*   **Topic:** "Кинь во все очереди, подписанные на `logs.*`". Гибкая фильтрация.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    RabbitMQ Exchange Types                                  │
└─────────────────────────────────────────────────────────────────────────────┘

 ═══════════════════════════════════════════════════════════════════════════
 DIRECT: Точное совпадение routing_key
 ═══════════════════════════════════════════════════════════════════════════

                          routing_key="error"
  Producer ──▶ [EXCHANGE] ─────────────────────▶ [error_queue]  ──▶ Consumer
                   │
                   │      routing_key="info"
                   └───────────────────────────▶ [info_queue]   ──▶ Consumer


 ═══════════════════════════════════════════════════════════════════════════
 FANOUT: Broadcast (рассылка всем)
 ═══════════════════════════════════════════════════════════════════════════

                                              ┌▶ [email_queue]    ──▶ Email Worker
                                              │
  Producer ──▶ [EXCHANGE] ────────────────────┼▶ [analytics_queue]──▶ Analytics
               (fanout)                       │
                                              └▶ [audit_queue]    ──▶ Audit Log


 ═══════════════════════════════════════════════════════════════════════════
 TOPIC: Pattern matching (logs.*, user.#)
 ═══════════════════════════════════════════════════════════════════════════

                          "logs.error"
  Producer ──▶ [EXCHANGE] ─────────────────────▶ [queue: logs.*]     ──▶ All logs
               (topic)    "logs.info"
                   │      ─────────────────────▶ [queue: logs.*]     ──▶ All logs
                   │
                   │      "user.created"
                   └───────────────────────────▶ [queue: user.#]     ──▶ User events

    * = один сегмент,  # = ноль или больше сегментов
```

### 7.2. Масштабирование (Scaling)

Что делать, если сообщений 1000/сек, а воркер обрабатывает только 100/сек? Очередь будет расти бесконечно.

*   **RabbitMQ:** Запускаешь еще 5 экземпляров воркера. RabbitMQ сам размажет задачи между ними (Round-robin).
*   **Kafka:** Тут сложнее. Единица параллелизма — это **Partition (Раздел)**.
    *   Чтобы 5 воркеров читали одну тему параллельно, у темы должно быть 5 партиций.
    *   Воркены объединяются в **Consumer Group**. Kafka гарантирует, что каждую партицию читает только один воркер из группы.

### 7.3. Надежность и Обработка ошибок (Reliability Patterns)

Это самый частый вопрос на собесах и самая частая причина боли в проде.

1.  **Dead Letter Queue (DLQ):**
    *   *Проблема:* Сообщение вызывает ошибку (баг в коде или битый JSON). Воркер делает `nack`, сообщение возвращается в очередь. Воркер снова берет его -> ошибка -> `nack`. Это бесконечный цикл (**Poison Message**). Процессор грузится, логи пухнут, другие задачи стоят.
    *   *Решение:* Настраиваем правило: "Если сообщение упало 5 раз — переложи его в специальную очередь `dead_letter_queue` и забудь". Потом разработчик разберет эту очередь вручную.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                   Dead Letter Queue (DLQ) Pattern                           │
└─────────────────────────────────────────────────────────────────────────────┘

                                    retry_count < 5?
                                         │
  ┌──────────┐    ┌────────────┐    ┌────┴─────┐    ┌──────────┐
  │ Producer │───▶│ Main Queue │───▶│  Worker  │───▶│ Success! │
  └──────────┘    └────────────┘    └────┬─────┘    └──────────┘
                        ▲                │
                        │     nack       │ retry_count >= 5
                        │ (retry < 5)    │
                        └────────────────┤
                                         ▼
                                  ┌──────────────┐
                                  │ Dead Letter  │◀── "Poison Message"
                                  │    Queue     │    (разбираем вручную)
                                  └──────────────┘

  ════════════════════════════════════════════════════════════════════════
   Без DLQ: бесконечный цикл ошибок → 100% CPU, забитые логи, stuck
   С DLQ: "плохие" сообщения изолированы, система работает дальше
  ════════════════════════════════════════════════════════════════════════
```

2.  **Идемпотентность (Idempotency):**
    *   *Проблема:* Сеть моргнула. Воркер обработал заказ, снял деньги, но не успел отправить `ack`. RabbitMQ думает, что воркер умер, и отдает задачу *другому* воркеру. Деньги списываются второй раз.
    *   *Решение:* Операция должна быть **идемпотентной** (повторный вызов не меняет результат).
    *   *Как:* Хранить ID обработанных сообщений в Redis/БД. Перед обработкой проверять: `if redis.exists(msg.id): return`.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                  Проблема без идемпотентности                               │
└─────────────────────────────────────────────────────────────────────────────┘

  1. Worker получает msg      2. Списывает $100    3. Сеть падает до ack

3.  **Backpressure & QoS (Quality of Service):**
    *   Если у тебя в очереди 1 млн задач, и ты запустишь воркер, он может попытаться выгрести их все сразу и упадет по памяти (`OOM`).
    *   В RabbitMQ есть `prefetch_count=10`. Это значит "Не давай мне больше 10 задач одновременно, пока я не подтвердил предыдущие".

### 7.4. At-Least-Once vs Exactly-Once

*   **At-Least-Once (Хотя бы раз):** Стандарт. Сообщение точно дойдет, но может продублироваться. (Нужна идемпотентность!)
*   **At-Most-Once (Не более раза):** "Выстрелил и забыл". Может потеряться, но дублей не будет. (Для логов не страшно).
*   **Exactly-Once (Ровно один раз):** Святой Грааль. В Kafka работает через транзакции, но дорого и сложно. Обычно дешевле сделать идемпотентный Consumer.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Гарантии доставки (Delivery Guarantees)                  │

## Итог

*   **RabbitMQ** — гибкий маршрутизатор. Идеален для задач "Сделай это" (Commands).
*   **Kafka** — мощная труба для данных. Идеален для "Произошло это" (Events) и Big Data.
*   **Junior:** Знает, как отправить и получить сообщение.
*   **Middle:** Знает, как не положить прод бесконечными ретраями (DLQ), как масштабировать воркеры и почему идемпотентность спасает деньги бизнеса.
